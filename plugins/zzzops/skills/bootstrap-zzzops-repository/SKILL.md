# Bootstrap ZzzOps

Communicate as [the shared guide](../../rules/COMMUNICATION.md) says, and respect its data boundary. Run the CLI as [CLI usage](../../zzzops/references/CLI_USAGE.md) says (without the `zzzops` launcher on `PATH`: `<python> ../../zzzops/zzzops.py`, Python 3.10 or later). Command reference: [CLI usage](../../zzzops/references/CLI_USAGE.md).

On a `legacy_policy` blocker (a pre-reset `.zzzops/POLICY.json`) or a `legacy` item, use the migrate-zzzops-repository skill; it calls back here for the policy files.

A checklist over the shipped templates, `zzzops validate` and plain `git`/`gh`. Nothing here is a ZzzOps verb. Templates: `../../zzzops/templates/default/` (`POLICY.json`, `workflow.json`, `prompts/`).

1. **Remote and integration branch.** Greenfield: `git init -b <I>` and push the first commit before any branch rules exist. Brownfield: use the existing trunk, or create `dev` from it and push.
2. **Write the policy files** into `.zzzops/` from the templates: `verification.commands` (the repository's canonical verify command); `required_ci` (only always-running required check names, read once with `gh api repos/{o}/{r}/rules/branches/<I>`); `integration_branch` = `<I>`; `goals.first_id` above the highest issue and PR number; `routing.tiers` trimmed to the harnesses in use. Capture the project's intent with the owner (`settings.intent`): what it is for (`purpose`), whom it serves (`serves`), what it deliberately is not (`not`), and the principles that must survive change (`principles`). Record their words; never write the intent for them. **If the `required_ci` read returns 403 or otherwise fails** (a private repo on GitHub's free plan has no rulesets or branch protection), do not retry, and tell the owner what was seen; the engine never reads rules, so nothing else breaks. Take `required_ci` from the owner, or if they do not know, propose the distinct names from recent PR check runs (`gh pr list --state merged --limit 5 --json number`, then `gh pr checks <n> --json name`, or `gh api repos/{o}/{r}/commits/<sha>/check-runs`). The owner confirms; the names must match the rollup `name` or `context` exactly. Set it now, before step 3, so the files landed in step 4 carry it. Never leave the list empty silently: an empty `required_ci` means integrate merges with no CI gate, so tell the owner so plainly, and if they decline a gate record that in the bootstrap commit or PR message (POLICY has no field for it). Tell the owner that on this plan the `zzzops/goal/**` deletion and force-push rule cannot be set or checked, and that merges are guarded only by the engine's required-check gate plus `--match-head-commit`; recommend making the repo public or upgrading if they want that rule
Before landing, write `.zzzops/TEMPLATE.json` with `policy_update.record.reviewed` from `zzzops validate --policy --dir .zzzops`, using a UTF-8 file tool.
3. **Validate:** `zzzops validate --policy --dir .zzzops` (needs no remote). It must pass with no `policy_update` item or `intent_placeholder` warning: every `TODO:` placeholder of the template's intent is replaced.
4. **Land the files** on `<I>`: through a `zzzops/policy/bootstrap` branch and a PR when `<I>` is protected, otherwise a direct push. A `zzzops/policy/*` branch pauses new work until it lands; before landing a change to an existing policy, preview it with `zzzops validate --policy-ref <branch>` and `zzzops next --policy-ref <branch>`.
5. **Per clone:** `git config zzzops.integrationBranch <I>` when `<I>` is not the remote's HEAD branch; `zzzops.remote` and `zzzops.committer` (`Name <email>`, identical on every machine) when needed.
6. **Harness setup:** follow [SETUP](../../zzzops/references/SETUP.md) (Codex profile or rules; Claude Code `permissions.allow`; sandbox domains; HTTPS remotes).
7. **Host settings (GitHub)**, checked with `gh api`: "Automatically delete head branches" on without `settings.branching`, **off** with it (merging a finish PR deletes the kept `release/N` or `hotfix/x` branch, and deleting a dependency branch can close or move stacked and release PRs before the engine retargets them); the merge method allowed matches `settings.merge.method`; a ruleset on `zzzops/goal/**` blocking deletion and force-push; `zzzops/**` excluded from every all-branch ruleset and hook rule (probe: `gh api repos/{o}/{r}/rules/branches/zzzops/lease/g0/x` lists no rules). If step 2 hit a 403, skip these rules probes and the ruleset checks (see step 2) and run only the repo-endpoint checks: `gh api repos/{o}/{r}` for `delete_branch_on_merge` and `allow_squash_merge`/`allow_merge_commit`/`allow_rebase_merge` against `settings.merge.method`; if that read is also 403, ask the owner to confirm them in the UI.
8. **CI and ignore files**, if the human agrees: `branches-ignore: ['zzzops/**']` on unfiltered `on: push` workflows and deploy integrations; skip `pull_request` jobs whose head starts with `zzzops/stack/`; add `.zzzops/worktrees/` to the repository's tool ignore files. Tell the human the repository's `pre-push` hook runs on work and PR branch pushes.
9. **Developer clones (optional):** `git config --add remote.origin.fetch '^refs/heads/zzzops/*'`.
10. **Run `zzzops validate`** (environment, Git version, SHA-1, not shallow, the harness probe, `gh`). With `settings.branching`, it warns if automatic head-branch deletion is still on and readable.
11. **Capture the first goals** with the add-goal skill.

## Update from the shipped defaults

A `policy_update` notice is advisory. Tell the owner which defaults changed and which were edited locally; updating or declining is their choice. For `newer_record` or `unknown_base`, upgrade the plugin before comparing; never offer the older plugin's default as newer.

1. Create a worktree from `<I>` on `zzzops/policy/defaults-<template>`. Keep the branch local until ready: pushing pauses new work.
2. In that worktree run `zzzops validate --policy --dir .zzzops`. Decide `workflow.json` first: read its MIGRATING section, then take, merge or keep it. Prompts follow that decision: copy an added prompt only if the chosen workflow uses it, and delete a removed prompt only if no longer named, regardless of `apply`. For other files, read each `diff` and perform its `apply`, or keep the local file. Resolve all markers. On Windows use `core.autocrlf=input` for this worktree or check the resulting line endings before committing. If `unknown_base` remains with the newest plugin, an unreleased build may have recorded it: explicitly set that `files` base to `null`, or delete its tombstone in `removed`, and compare that file once by hand.
3. Write `record.reviewed` to `.zzzops/TEMPLATE.json` with a UTF-8 file tool after reconciling each file. For `no_record`/`invalid_record` without a review, write `record.inferred` instead: it records known history matches and leaves customized files unknown. To decline, change only the record to `record.reviewed`; the PR explains the declined defaults. Unknown bases are preserved; when all listed files are unknown, no reviewed record is offered.
4. Re-run `validate --policy --dir .zzzops`: require no errors, no `policy_merge_markers`, and no `policy_update` after a full review (inferred records can still show drift). Commit and push, preview with `zzzops validate --policy-ref <branch>` and `zzzops next --policy-ref <branch>`, and put the taken/kept/declined decisions and impact in the PR. Land through the repository's review/approval path and delete the branch. Prompt text alone does not stale records; bump the relevant node's `rev` if the changed semantics require another review.
