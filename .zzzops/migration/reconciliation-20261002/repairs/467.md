## Outcome
Make each source-changing workflow `next_step` name the immutable Git commit it must be based on, alongside the predecessor branch or PR when applicable. Agents must receive enough information to start from the intended linear stack tip without inferring ancestry from prose or local branch state. The active worktree may contain in-progress commits above that base; it must not be based on an older stack tip.

## Acceptance criteria

- Publication and implementation next steps include a deterministic base commit and its branch or PR context.
- Before source-changing work begins, the CLI verifies that the active checkout is based on the latest valid required stack tip, resolved from current repository/provider evidence. The agent's HEAD may be ahead with in-progress work; it need not equal the tip.
- If the required tip advances, the CLI returns a repair step naming the new base and preserves in-progress work. It must not silently reset, discard, or overwrite local changes; it revalidates the base before subsequent source-changing work and publication.
- The CLI detects a stale or sibling base before publication and returns a repair step that names the current required tip.
- Integration coverage proves a split PR chain cannot proceed, a valid linear native stack can, and an out-of-date checkout is safely repaired or blocked without losing work.
- The guidance is derived from current repository and provider evidence, not stored as mutable workflow state.
