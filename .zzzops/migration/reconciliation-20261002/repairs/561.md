Support the documented Codex cachebuster version suffix without requiring its removal or weakening proof that the installed ZzzOps package matches the intended implementation.

## Acceptance criteria
- A valid cachebuster produced by the documented Codex helper is accepted when its underlying product version matches the canonical ZzzOps version; no manual suffix removal or prompt-metadata regeneration is required solely for cache invalidation.
- Preserve checks for plugin identity, underlying version, required package files and generated skill metadata. Different underlying versions, malformed cachebuster values and unrelated version mismatches remain actionable validation failures.
- Package provenance and installation-validation signatures continue to reflect the complete actual package contents, including the full cachebuster manifest. A suffix change or code/content change invalidates stale validation evidence; accepting a suffix never establishes that code is latest.
- Keep product-version and cachebuster identity distinguishable in diagnostics/provenance where necessary to explain installed-build identity. Preserve existing released package behavior and avoid silently stripping arbitrary version metadata.
- Regression tests reproduce the standard helper workflow and cover unchanged packages, valid suffixes, base-version/name mismatches, malformed suffixes, stale skill metadata, changed content and distinct suffixes producing distinct content digests. Verify the public installation-validation path accepts the valid package and retains current-package audit binding.

## Scope and constraints
Bounded package-version compatibility and directly related validation/provenance diagnostics and tests. Determine the exact normalization boundary during understanding; do not replace content hashing with version equality or modify manifests/prompts merely to hide a mismatch. No plugin installation, marketplace/config change, unrelated source edits, cleanup or deployment is authorized by capture.
