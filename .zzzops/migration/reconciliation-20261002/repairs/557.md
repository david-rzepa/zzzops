## Outcome

Make ZzzOps understand why tests exist, which changes require them, and how to execute them efficiently. Maintain one Git-tracked repository test-plan file containing test definitions, goal provenance, dependencies and latest successful input hashes. Use it to select dirty tests deterministically and to resume bounded verification partitions without rerunning completed matching work. Full-suite verification remains available through the same machinery.

## Reviewed requirements

The user explicitly selected one mutable tracked file containing both the test plan and latest successful input hashes. Git history supplies historical records; do not require an append-only collection of immutable per-test files or an external authoritative success ledger. An optional disposable cache may accelerate lookup. Exact path and schema are implementation decisions for independent review.

Each test or test group records its purpose and the observable behavior it protects, its originating durable goal and specification reference/hash where available, and later goals that extend it. Existing tests with unknown origins remain explicit unknowns; do not invent provenance. Goal output scopes describe permitted edits and are distinct from the verification execution plan.

The latest success binds a complete combination of test IDs/content, relevant source dependencies, fixtures, runner, dependency/configuration/environment identities, and the semantic test-plan definition. Use content hashes rather than Git status or a single global last-run pointer. The result metadata portion of the plan does not hash itself; changes to definitions, dependencies, discovery, runners or policy do invalidate affected results.

## Acceptance criteria

- Maintain one Git-tracked test-plan file containing current test entries and their latest successful input hashes/result summaries. Deterministic serialization and stable identities produce reproducible updates without timestamps or volatile data causing unnecessary changes. Raw logs may live elsewhere behind verified references; they are not another authoritative plan or success ledger.
- Every test/group has a stated purpose, runner/selection, goal provenance where evidenced, relevant input dependencies and an explicit completeness/fallback contract. Record unknown origins and dependencies honestly. Preserve multiple contributing goals when a test protects shared behavior.
- Deterministically select tests for changed work from the reviewed dependency mapping and acceptance obligations, including transitive dependencies. Unknown or incomplete mapping widens the run conservatively. Arbitrary agent claims and a file's edit scope cannot justify skipping required tests.
- Dirty checks use actual content identities, including relevant uncommitted/untracked inputs and missing/deleted files, test bytes/IDs, fixtures, lockfiles, relevant configuration/environment and runner versions. Unrelated changes leave unaffected complete mappings reusable. Changes to test inventory rebuild coverage obligations. A prior successful record for separate inputs cannot prove their new combination passed.
- Checking out an older verified commit carries its matching test-plan success records and does not become dirty solely because a newer commit was tested elsewhere. Changing commit metadata while relevant bytes remain identical may reuse local evidence; exact-head CI remains separately enforced where policy requires it.
- Exclude latest-result metadata from its own input fingerprint while including semantic plan definitions and verification-tooling changes. Verification may update only authorized plan result fields without falsely appearing to change tested product inputs. Reject unauthorized definition/source changes during a run.
- Discover a frozen complete test inventory through supported project-native runners, then partition it deterministically into bounded executable units. Use observed durations to avoid command timeouts without flaky performance acceptance thresholds. Partitioning preserves the exact inventory with no missing/duplicate tests and respects declared order/shared-state constraints. Unsupported opaque commands remain explicit units; no unsupported claim of test-level resumability.
- Record progress and each completed partition durably before proceeding so interruption, cancellation, uncertain transport, process crash or a later timeout cannot lose successful completed work. Preserve stable request/partition identities and determine whether a prior executor is still running or already completed before retrying; never duplicate live work.
- Distinguish passed, assertion-failed, timed-out, cancelled and infrastructure-error outcomes. Timeout is incomplete evidence, not proof of a failing product test and not an aggregate red baseline. Keep completed matching passes; retry or safely subdivide only incomplete/timed-out work. A single unpartitionable slow test produces an actionable blocked/incomplete result rather than a false pass.
- Resume from existing passing partitions only after rechecking their complete input fingerprints, inventory, log integrity and current ownership/authority. A new lease may reuse matching execution facts but must assemble a new current phase proof; stale approvals, acquisitions or prior coordination never regain authority. Known newer failures for identical inputs cannot be hidden by an older success.
- Support changed-work, explicit selection, expected-red baseline and full-suite modes. Red baseline success requires the intended assertion/signature on the specified baseline, never any nonzero exit, import failure or timeout. Keep separately owned unfinished-goal baseline tests out of another goal's green gate while reporting them honestly.
- Full-suite runs freeze all required test IDs and runner/environment/platform obligations, shard them through the same resumable engine and aggregate only current complete results. Existing matching partitions can be reused when their declared inputs match; show what ran and what was reused. No aggregate pass is possible with missing, stale, failed or incomplete required partitions.
- Keep exact-head CI/platform and review/publication requirements intact. At publication verify that required results match the candidate's source/test content and semantic plan. Permit testing the working tree, writing matching result metadata and committing code plus plan together; avoid a self-referential final commit hash embedded in its own commit. Required provider CI still binds the exact PR head.
- Validate inventory and dependencies after merge/integration. Agents resolve test definition/provenance entries properly within the single branch stack. Either side's result hashes may be selected during conflict resolution, then deterministic matching reruns stale partitions. Lost/deleted/duplicate test entries cannot silently shrink verification obligations.
- Persist compact progress without one backend comment per test or duplicating logs. Maintain bounded recovery state and deterministic repository updates; preserve historical evidence/legacy verification contracts through reviewed migration. Capture/admin must not initialize target plans or alter worktrees.
- Regression/integration tests prove late timeout recovery without repeating earlier passes, safe splitting, uncertain-response recovery, cross-lease reuse, content/dependency/environment invalidation, older-checkout validity, self-hash exclusion, merge inventory integrity, correct red-baseline classification, full-suite completeness and exact-head publication gates. Measured invocation counts demonstrate only dirty/incomplete work repeats and no required coverage is weakened.

## Scope, architecture and boundaries

Extend the installed public CLI verification path, its durable progress/recovery and phase-proof assembly, repository test-plan integration, project-native runner adapters, policy/skill guidance and focused regressions. Start with evidenced repository runners and finite supported adapters; missing runner capabilities must produce explicit bounded fallback behavior. A deterministic planning preview explains selection, dirtiness, reuse and remaining obligations before execution.

Default to serial partitions. Parallel test processes require reviewed resource/parallelism authority and safe isolation, and do not implicitly authorize extra agents or additional branches. Keep one active branch stack and reviewed ancestry/integration order. Do not delete tests, weaken checks, introduce semantic-AST cache shortcuts or claim dependency mappings are complete without evidence.

## Evidence and first falsifiable probe

Observed installed workflow.py verify runs a supplied command list sequentially with a hardcoded 300-second per-command timeout, collects results and writes one aggregate proof after all commands. Timeout raises before aggregate persistence; earlier passing commands therefore lack a reusable successful proof. Current acquisition proofs bind workspace, exact commands/log hashes, actor and lease.

Goal #539 verification exposed repeated costly retries: focused codec/history/owned-output checks passed 88 tests with four skips in approximately 170 seconds; test_zzzops required four initialization slices plus a 249-test remainder to avoid timeout. Three other declared modules were approved #498 preimplementation graph/schema tests and remained red against schema1 production, demonstrating why edit scope and green verification obligations must be separate.

First probe: use a bounded fake project-native runner with three disjoint test partitions. Complete the first two, time out/interruption the third, resume with the same input identities, and assert the first two each executed exactly once while the incomplete partition is retried/split. Then change one declared dependency and assert only its affected partition becomes dirty; change an unmapped relevant input and assert conservative widening. Repeat using two Git checkouts containing different tracked plan/success snapshots to prove branch-local validity. Build this narrow harness before implementation edits.

## Risks and governance

Primary risks are false-green reuse from incomplete dependencies or environment identities, lost tests after splitting/merges, record updates invalidating themselves, order-sensitive tests changing behavior under partitioning, uncertain process completion and reuse bypassing acquisition/review authority. Independent design/test/implementation review must address these directly. The prior requirements discussion and instruction to create this goal approve capture of this spec, not implementation, merge, release or additional external operations.
