# Optional pre-test contract scaffolding

## Outcome and evidence

The design reviewer, not the test writer or a mandatory extra worker, decides whether a goal needs a contract scaffold. If not, the delivery path has no scaffold worker or scaffold-review worker. If yes, the scaffold is made and independently reviewed after the goal's base is prepared and before tests are written. Existing interfaces remain the normal fast path. A scaffold supplies the smallest callable public or internal contracts and composition needed to express a real failing behavior test; it does not satisfy the behavior being tested.

At integration tip `cb33c2d` the shipped graph is `design → review_design/filter_design → approve_design → base → test_design → review_tests → implement`. Review nodes have only implicit `decision`/`summary`/`report` outputs (`schemas.py:224,491,1323`). The frontier only recognizes explicit goal skips, and `optional` waits for a producer to complete or be skipped; it is not a conditional branch (`frontier.py:72–92,248–254`). The test freeze records whole changed paths (`verbs.py:frozen_paths`), so a mode-160000 submodule path would freeze every future pointer update. Neither a prompt-only optional edge nor an untyped sentence in a review summary can safely implement the requested flow.

## Graph and engine contract

1. Add a small, generic, capability-gated workflow feature for a typed optional routing declaration on an agent review and a boolean predicate on nodes. In the shipped graph `review_design` declares a required boolean output `scaffold_needed` and a short review-report rationale. This is an explicit, validated machine-readable output, not parsing prose. Do not add it to all reviews: existing review nodes have implicit outputs only, so extend schema/output validation and card generation only for review nodes that opt in. Include it in node/output identity and check the decision is present on a completed review. The review prompt examines the actual design and integration source, asks whether real callable contracts/registration/test seams must be introduced before meaningful red tests, and sets the flag. A changed flag must stale route-dependent nodes; a repeated review of unchanged source must be deterministic where the decision is unchanged.
2. Add a narrowly typed conditional predicate referencing a boolean output of an ancestor (`review_design.scaffold_needed`) rather than evaluating arbitrary code or free-form expressions. The frontier waits for a *current* producer and its required ancestor/filter/design-approval gates. Only literal false produces an explicit derived `skipped` state, including reason and producer identity; missing, stale, invalid or blocked review is never treated as false. True enables the ordinary node. Integrate the predicate into graph acyclicity, selector type checks, input fingerprints, `next`, cards, dry-run/policy previews, and stale/live-lease handling. Derived skips do not mutate `goal.skip`, overwrite an explicit human skip, or consume a worker/review/budget. A false→true or true→false re-review stales affected downstream records using normal rules; open findings and previous evidence remain visible. A user-selected skip cannot bypass mandatory reviews or erase a material finding.

   Route changes must also invalidate the decision path itself. Declare `review_design.scaffold_needed` as an explicit typed, fingerprinted input to `adversary_design`, `filter_design`, and the `approve_design` review context (including the reviewed design and route producer identity). Change their definitions/selectors and fingerprint rules as needed so a boolean change makes the adversarial challenge, filter and owner approval stale even when their prose summaries remain byte-identical. A new filter and approval are required before `base` or either downstream route resumes; respect live leases and preserve historical records and findings. This is a dependency on the completed primary review, not a circular dependency on the filter output. Test actual frontier/CLI behavior on a boolean-only flip with unchanged summaries; assert stale states and that no downstream action can start until the new gates complete.
3. A true→false route change is fail-closed if a scaffold checkpoint, live scaffold lease, or open material finding for scaffold/review exists. Keep that prior work and its findings visible; the proposed false route is pending, not a derived skip that unlocks `test_design`. Allow resolution using the prior true-route repair/review path, or explicitly waive findings through the existing authorized waiver mechanism. Waiver alone does not make unreviewed code acceptable: any retained scaffold checkpoint must have an independently approved current review for the exact retained checkpoint, with all material findings resolved or explicitly waived. Otherwise require a separate reviewed transition that reverts/removes the affected scaffold code and verifies its resulting checkpoint before false can take effect. Do not drop records, silently reset code, cancel a live lease, or let resolving a finding alone bless a changed checkpoint. Once those conditions and the re-run design/route approval gates hold, record the transition evidence and allow the derived skips; preserve existing audit history. Cover unresolved findings, a waiver with unreviewed retained code, a reviewed retained checkpoint, and reviewed removal in real workflow tests.
4. Introduce an agent scaffold node after `base`, enabled by that predicate. It uses the normal goal workspace/checkpoint and conventional commits. Define only contracts, data shapes, minimal registration, and controlled seams needed to run tests; use explicit not-implemented/failing paths where needed. Do not implement the new feature or introduce fake success. The node documents any externally consequential owner choice using the existing `owner_questions` path; routine internal seam decisions are its own. Review the resulting checkpoint with a separate independent `review_scaffold` node, enabled by the same predicate and required when true. The review checks contract coherence, user decisions, unintended behavior/side effects, reusability and that future tests can reach the real production registration. It may send findings back to scaffold or design, using ordinary review rules.
5. Gate `test_design` on the scaffold review and checkpoint only when selected: conditional producers yield a legitimate skipped value to an `optional` selector when false; they never let an unfinished scaffold pass on true. Preserve the existing `base.base_commit` SHA input for checkpoint semantics; tests run against the current worktree containing the reviewed scaffold. If tests uncover a needed scaffold seam, raise a finding to the appropriate ancestor rather than fabricate an unused helper or weaken a test. An externally meaningful change goes through an owner question; a routine internal seam is revised and independently reviewed without requiring the owner to approve an unchanged design again. `implement` remains the separate behavior phase and must preserve all accepted tests. A false path must run the existing design→tests→implementation route unchanged apart from the recorded review decision; no extra agent is dispatched.
6. Add an explicit capability (e.g. `conditional_review_routes`) and reject policies using the feature when unsupported. Upgrade all writers before adopting a policy that requires it; do not let an older writer interpret a false route as runnable. Keep old graphs and records valid in the new engine. Ensure filtering/approval does not accidentally turn a pending review into a false decision: `base` still waits for the existing `filter_design` and `approve_design`, and both enabled scaffold nodes wait on that base as well as the current decision. Lenses remain independent; the primary design reviewer owns the route decision, while the adversarial reviewer can challenge it through findings and the filter.

## Package and submodule boundaries

Do not treat a superproject gitlink as a frozen test file. For each explicitly declared Git submodule touched in test authoring, record a deterministic child baseline: the child gitlink at the accepted pre-test parent checkpoint (after any scaffold); record that parent checkpoint, child repository identity and baseline commit/tree. At each accepted test checkpoint, derive the protected union from **all** child paths changed from that baseline through the accepted test checkpoint, plus all previously accepted child protected paths on retries; do not select by filename, worker declaration or a list of presumed test files. For retry histories retain prior union and include the full verifiable chain of test-authoring changes/checkpoints since that baseline, including blocked attempts, so a change and later restoration is not omitted merely because the final tree matches. Use deterministic no-rename tree diffs: a rename protects both old and new paths; record exact accepted tree entries (mode, type, object ID, and an explicit absent marker for deletions) for additions, deletions, helpers, fixtures, configs and every other changed entry. Preserve these records and baseline/checkpoint provenance as immutable reviewed evidence. If the baseline, prior union, history, mapping, accepted child trees or full scope cannot be verified, fail closed with an actionable diagnostic rather than infer a smaller scope. Permit a child pointer to advance to an implementation descendant only after verifying every protected child entry still exactly equals the accepted entry; do not use whole-child-pointer equality as the preservation rule. Protect superproject test files normally. Scaffold and test work in package repositories stays in their owning repositories and uses separately reviewable branches/PRs and their existing approval authority; the superproject records only reviewed, resolvable gitlinks and evidence. No implicit remote write or package merge is authorized by this design.

The current engine's Git identity is superproject-only and has no child-tree preservation. Add the smallest capability-gated, Git-aware checkpoint extension needed for this behavior, rather than disabling preservation. Child object lookup must validate repository/path identity against the checked-out `.gitmodules` and requested gitlinks, treat missing or ambiguous child objects, unauthorized/untrusted locations, rewrites and unreviewed child tests as actionable blockers, and avoid credentials in logs. No unbounded or hidden fetch. Limit the first implementation to the submodule forms exercised by the project's fixture, explicitly reject unsupported nesting rather than silently dropping protection. On integrate/squash and base/sync, verify both child protected entries and the final superproject gitlink; keep the reviewable child-commit provenance. Coordinate with G1049's preservation fix without assuming its unreviewed design or silently waiving its finding. If a working generic child protection mechanism cannot be implemented in this goal without materially expanding the product contract, the designer must raise that to review/owner, not turn preservation off.

## Alternatives, risks and non-goals

An always-dispatched agent that may no-op is mandatory overhead, contrary to the goal. Existing explicit skips force recurring coordinator/owner action and cannot make the reviewer decide the route automatically; free-form summary parsing is unsafe. A prompt-only seam without checkpoint enforcement invites unreviewed implementation changes. Freezing a whole submodule or simply excluding it either blocks real implementation or silently weakens accepted tests. Building a general cross-repository CI/deploy platform and automatically migrating all installed policies are out of scope. Main risks are routing on stale review data, newly required outputs stranding in-flight goals, added engine/schema compatibility, child-repository provenance/availability, and scaffold code implementing behavior prematurely; use capability floors, truthful preview and failing-closed tests. G1049 remains separately responsible for the existing blocked-record frozen-scope defect and recovery.
