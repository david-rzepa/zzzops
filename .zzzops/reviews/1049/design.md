# Preserve frozen tests across blocked retries

## Outcome

A preserved test producer retains its previously accepted test-path scope when it blocks, retries, or is invalidated and rerun. Later accepted test changes are added to that scope; an implementation changing any protected path is refused and review covers the complete accepted scope. An affected repository can reconstruct its scope from its own Git goal history, apply a reviewed recovery through the existing `validate`/`edit` workflow, and independently re-review the resulting test checkpoint without changing its test content or fabricating checkpoint identities.

## Evidence and constraints

At the integration tip, `blocked_record` calls `records.record` without a `frozen` extra and `frozen_paths` reads the old list only when the prior record's status is `done`. Consecutive blocked attempts therefore lose the list regardless of whether the optional `blocked_findings` capability saved `last_output`. A later successful submit scopes `Identity.change` and `preserve_check` to only the paths changed since its lease; published producer commits made before a block are also missed by that retry. Separately, `preserve_check` returns when the producer is blocked, so a previously published implementation tip may evade the per-commit scan. `validate_record` already permits `frozen` on either record status, so retaining that field needs no goal-schema expansion.

Project Base G12 demonstrates the defect. Its goal commit `162d60c` records 13 frozen paths at test checkpoint `ad39eb5`; blocked attempt 7 at `dd6be0a` lacks the list; done attempt 8 at `b493523` records two paths at later checkpoint `082177c`. Both paths are among the earlier 13, and all 13 exist in that later checkpoint. Its current attempt 9 (`3c72a5e` at investigation) is blocked with neither `frozen` nor `last_output`. Do not mutate that goal as part of this design; re-read all live tips and evidence before any later recovery.

## Engine change

### Producer-attempt provenance and blocked-consumer safety

A blocked producer may already have published commits that are absent from the next attempt's lease diff. Capture each preserved producer attempt's exact start work tip and synchronized blocked work tip as a pending provenance segment, fenced to that producer, attempt, lease and goal. Persist these segments through consecutive blocked records alongside the last accepted checkpoint identity and frozen scope; record the segment in the same compare-and-swap transaction as the blocked record and work-ref update. A retry also captures its own final segment. Retain the immutable commit objects, not just filenames or a movable ref. Segment endpoints must be verifiable, ordered, belong to the corresponding valid producer lease, and have ancestry consistent with the next segment/checkpoint. Do not infer authorship from timestamps, unrelated branches, or the entire base-to-tip work diff.

At successful producer submit, derive candidate changes from every verified producer segment plus the current lease-to-checkpoint segment using code-tree diffs, excluding submodule gitlinks and non-code trees as today. Carry the prior accepted frozen scope even when it was recorded before the block, then union accepted new test paths from those candidates. A no-op retry must still see candidates created before the block. When ancestry is rewritten by a supported base sync or rebase, carry verified old-to-new mappings furnished by that operation; if equivalence and attempt attribution cannot be proved, refuse the submit with an actionable request to rerun or explicitly reconstruct the producer's scope. Never substitute a broad diff that sweeps in implementation work. If candidate changes include files whose membership in test scope cannot be established, require the producer to explicitly identify the accepted test paths in the successful checkpoint and present the entire candidate set and exclusions to independent review; reject unverifiable inclusions and never silently freeze unrelated source files. A path touched during a blocked attempt becomes accepted only when included in the later successful producer checkpoint and its review, not when the attempt blocks. An explicit selection is not evidence that excluded tests were safe: the review sees every candidate and judges omissions.

When a node's `preserve` producer is blocked, refuse that consumer's successful checkpoint submissions until the producer has successfully resubmitted and is available for the usual preservation check. This rule applies even if `blocked_findings` is disabled or no `last_output` exists. It eliminates both the already-published-work-tip loophole and the need to treat an unreviewed blocked artifact as an accepted checkpoint; the producer's own test corrections remain allowed. Preserve the last accepted checkpoint and scope as immutable provenance for restoration and diagnostics, but do not falsely expose it as a current successful producer output. Include a useful refusal explaining how to resume the producer. The same rule applies to every submit path capable of publishing a checkpoint; audit all such paths, not only the per-commit scan.


1. For an agent node that produces a checkpoint preserved by another configured graph node, carry the exact last recorded `frozen` list into a new blocked record when present, including across repeated blocks. Do not copy it to unrelated nodes, change the blocked output to a successful output, overwrite findings or answers, or infer a protection scope from arbitrary worktree changes. Keep the field and the verified accepted-checkpoint/attempt provenance on a blocked record even when `blocked_findings` is not required. Extend record schemas and capability-gate the added provenance fields; the existing `frozen` field itself already supports blocked records. Preserve the difference between a missing field (legacy/unscoped, not proof of an empty scope) and an explicit empty list.
2. When a preserved producer subsequently submits, have `frozen_paths` retain an existing valid scope from either `done` or `blocked` records. Union it with the verified per-attempt candidate segments and final lease-to-checkpoint change set described above; retain deterministic ordering and the existing no-renames/code-tree rules. Check deletions, rebases and sync merges against the current supported ancestry rules. Do not fall back to a broad base-to-tip diff merely because a retry blocked: that can freeze unrelated source or submodule gitlinks. Non-preserved nodes and projects without a scope retain their existing behavior. Legitimate reviewed test corrections remain possible through the producer; implementation's `preserve_check` and per-commit checks must continue rejecting changes to accepted tests.
3. Introduce an engine capability for the new blocked-scope guarantee. Require the new capability before writing the new provenance fields, and have old engines refuse to write once it is required. Before activation, preserve compatible existing `frozen` fields and block unsafe preserved-consumer submissions; if a producer block would publish unrecordable pending work, refuse that operation with an actionable capability-upgrade instruction rather than lose provenance. An older writer can still repeat the loss until all writers are upgraded and the capability is required, so emit a clear advisory; do not silently loosen an existing minimum. Activate through ordinary reviewed policy change. The capability identifier is `preserved_test_provenance`; it appears in the existing `validate` response at `engine.capabilities` and is added to `settings.engine.requires` through the normal reviewed policy upgrade. Recovery and blocked-producer refusal messages name that exact capability. Older writers must reject a policy requiring this identifier.

## Recovery through existing commands

### Observable validation and edit contract

`zzzops validate G` remains read-only and adds `scope_recovery` as an object keyed by decimal goal ID strings for explicitly requested goals. Each value is an array of diagnostics, one per configured preserved producer needing attention; an unaffected goal has an empty array. Each diagnostic has `producer` (node ID), `status` (`proposal` or `uncertain`), `goal_commit` (the full observed goal tip), `producer_state` (record status), `paths` (deterministically sorted array), `proposal`, and `issues` (array). Each `paths` element has `path` and nonempty `sources`, sorted deterministically; each source has `goal_commit`, `attempt` (integer), `checkpoint` (full immutable checkpoint commit), and `checkpoint_base` (full base commit). These are exact field names and JSON types; additional fields may be added without changing these. `proposal` is null when evidence is insufficient. In `uncertain` status, `issues` is nonempty and describes why there is no safe proposal. In `proposal` status, `issues` is empty, and `proposal` is an object with `base` equal to `goal_commit` and `edit` containing an exact JSON edit-file object in the existing `{"set": {"records.<producer>.frozen": [...]}}` format, plus any other necessary validated `set` entries. The exact embedded `edit` object must be serializable as UTF-8 JSON and consumed without transformation by `zzzops edit G --file FILE` for preview and `zzzops edit G --file FILE --base BASE` for the guarded write. It is not itself a write or a shell command. For a done producer the proposal must include all fields needed to recompute the protected checkpoint identity and trigger correct review invalidation, or be `uncertain` and require a producer resubmit as described below. Tests create their edit file from this response, inspect per-path provenance, and exercise the actual edit/preview/CAS flow. The field is additive; existing `goals`, `engine`, warnings and error behavior remain unchanged, and plain `validate` without explicit goal IDs does not scan every historical goal or fabricate proposals.

The writer revalidates the proposed repair against current accepted-history provenance at apply time rather than trusting a caller-modified JSON object. A stale goal base, changed work history or conflicting lease must refuse the write; only the requested goal and producer may change. `status=proposal` reports evidence, not owner approval, and does not waive any finding. Document the JSON fields and require compatible additive changes; internal segment storage remains an implementation detail.

Extend goal validation with a read-only, provenance-bearing diagnostic for a suspected lost scope. Walk the accepted goal branch's available Git history in order, collecting only prior valid `done` records of the same goal and configured preserved producer, with their `frozen` scopes and checkpoint commit/base/tree identities. Reconstruct a proposed union from relevant accepted records and show each path's source goal commit, producer attempt and checkpoint, the current goal tip, current producer state and latest accepted checkpoint. Validate that referenced objects exist and that their ancestry and identity are compatible with the current goal/work history. Preserve paths whose accepted tests were legitimately deleted as protected paths where provenance warrants it; never silently include unrelated gitlinks or source paths based on an unscoped tree diff. If histories are missing, rewritten, merged ambiguously, malformed, or contain conflicting scopes/checkpoints that cannot be proved, report the exact uncertainty and make no automatic repair proposal. Do not assume every goal with no `frozen` field is damaged: old records may intentionally be legacy/unscoped.

For a provable case, validation produces a concrete existing `zzzops edit` file and the exact observed `--base` goal commit as a preview, not a write. The operator reviews its path-by-path provenance, confirms no live lease could race it, upgrades the writers and enables the required capability, then applies the existing `edit --file … --base …` command. A concurrent goal change must cause the existing base check to refuse it. The engine must validate that the proposed restoration has a coherent accepted-history provenance and no unexplained paths; `edit` remains an explicitly reviewed repair rather than an automatic mutation on read. The Git goal commit provides an auditable field diff; retain and show the historical commits supporting it. Do not edit history, rewrite old records, close or waive findings, modify test files to make them appear changed, or mark a phase current by hand.

For a currently blocked producer such as G12, restore the proven union to its blocked record, then rerun the real producer under the fixed engine; it will retain the union and calculate the scoped `change` against the real submitted checkpoint. The original review finding remains live and the resulting test review must be rerun independently. For a currently done producer, do not simply widen `frozen` while leaving a stale scoped change identity: recovery must recompute and verify the checkpoint's scoped `change` using its unchanged recorded base, commit and code tree, and ensure dependent reviews are invalidated and rerun. If that cannot be demonstrated under the normal fingerprint rules, require the producer to resubmit under the fixed engine instead of pretending its old review covers the widened scope. Recovery is complete only when the independent test review observes the whole scope and an attempted implementation edit to each protected path is rejected.

The advisory must remain bounded to the explicitly requested goal and be idempotent: an already-correct or unaffected goal offers no write. Respect a no-write `validate`, current lease checks, supported read-only previews, and full clones. Record the operator's reasoning and source commits in the repair documentation/evidence; the source of truth remains Git. The exact recovery output is additive to current validation output; normal `edit` CAS, audit and validation remain in force.

## Verification

- Include a real CLI/Git regression where the producer commits a new test during a blocked attempt, publishes the blocked work tip, and succeeds on a no-op retry: the new test must enter the accepted and independently reviewed frozen scope. Repeat for multiple blocks and a verified sync/rebase, and demonstrate refusal when provenance cannot be verified. Include candidate source files and gitlinks to prove exclusions are explicit and reviewed, not silently frozen.
- Include an already-published implementation work tip modifying an accepted test while the producer is blocked and `blocked_findings` is disabled; consumer submission must be refused regardless of whether the per-commit origin-to-head range is empty. After retry and acceptance, both final-tree and per-commit checks must reject it. Verify non-test edits remain possible after the producer resumes.
- Unit tests around record construction and `frozen_paths` cover done → blocked → done, multiple blocks, blocked_findings on/off, no prior record, explicit empty versus absent scope, unchanged/ancestor and forward checkpoints, independent new test paths, deletes, sync merges, goal isolation and non-preserved nodes. Assert no unrelated source or gitlink enters scope.
- End-to-end local Git remote tests drive actual CLI start/submit/blocked/retry and assert every retained and newly accepted test path is refused by both per-commit and final-tree implementation protection; permitted non-test implementation changes succeed. Cover legitimate test correction through the producer and subsequent independent review, including scopes and fingerprint staleness.
- Build a fixture reproducing G12's sequence and full 13/2/subset history; run read-only recovery analysis, inspect evidence, preview and CAS-apply using the supported `edit` route, retry the actual producer, then require a fresh independent test review. Check the later real checkpoint and open findings survive, protection is the proven union, and historical goal commits are unchanged. Validate done-state recovery separately. Re-run recovery idempotently; demonstrate refusal on stale bases, missing history, inconsistent or unrelated paths, ambiguous ancestry, live conflicting leases and unknown/older engines.
- Exercise old records without `frozen`, records already containing it, older project graphs, and old writers before/after the capability gate. Check validation output is additive and existing automation continues to parse it. Measure focused local tests, then run the repository's configured real integration checks, including image/release checks where required; report unavailable external dependencies rather than replacing them with mocks.

## Alternatives and limits

Always using the base-to-tip tree diff can freeze implementation files and submodule gitlinks. Recreating test changes merely to trigger path detection adds noise and falsifies their provenance. Automatically rewriting a historical record or silently widening a current reviewed checkpoint can falsely claim tests were reviewed; explicit evidence, normal CAS and independent re-review avoid that. Keeping only the last output is insufficient when `blocked_findings` is disabled, as G12 demonstrates. This change does not alter product test content, change another project's policies automatically, deploy software, or directly mutate Project Base G12; its actual recovery is performed only after the engine and recovery flow are implemented, validated and available to every writer.
