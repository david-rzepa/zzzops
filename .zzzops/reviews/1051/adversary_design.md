# Adversarial review: G1051 design

Changes requested. The component ordering and canonicalization address the stated examples, but two operational races can defeat the release isolation guarantee.

1. **An inserted member can finish on integration before the new line exists.** At the integration tip, `lines.target_of()` directs an ordinary release goal to the integration branch whenever its named release line is not yet open. The proposal allows an owner to add or retarget an open goal to an earlier target and says the inserted line must be created before member goals merge, but does not make that ordering an enforced precondition of `base`, integration, or goal closure. A scheduler can therefore finish such a goal on integration before the human creates the inserted patch line. The line can then be cut from production, which excludes the already-closed goal's change, yet release membership/finish checks may see that goal as completed. Enforce waiting for an approved, correctly based inserted line before any member work starts or merges; also detect and refuse or explicitly recover already-completed member goals whose changes aren't in that line. Cover the race between retarget/creation and worker dispatch with a real remote fixture.

2. **An external production update can race patch-line creation after the approved base is checked.** The design requires refusing when production has advanced beyond the intended base and mentions leases/CAS for competing line operations, but does not specify an atomic guard on the production ref used to create the new branch. At the integration tip `lineverbs.run()` atomically pushes the new goal and new branch, not the source production ref; a user or external workflow can advance production after the preflight reads the approved source commit and before that push. The engine can then publish a patch line based on an obsolete production release and incorrectly consider the approved base current. Specify how production is guarded against a direct remote update at the commit point, or revalidated with a safe non-destructive protocol that prevents any member from starting or merging on a stale line; require a real remote race test where production advances between approval/preflight and creation. Leases scoped to ZzzOps workers alone do not control external pushes.
