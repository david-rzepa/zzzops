# Insertable dotted target releases

## Outcome

A repository can target an ordered patch such as `2.1` even after `3` has been cut, without renumbering or implicitly reassigning goals already targeting `3`. `2`, `2.0` and `2.0.0` identify one target; `2.1` and `2.10` remain distinct and sort numerically by components. Identifiers have arbitrarily many finite numeric components: `2 < 2.0.0.1 < 2.0.1 < 2.1`, allowing further targets to be inserted between existing targets. A patch line can be based on the released code and delivered without including work from an unrelated later release. Existing approvals and release-line finish gates still apply; ZzzOps does not publish a package or deploy anything.

## Current behavior

At integration commit `cb33c2d`, `schemas.py` accepts only integer `goal.release` and `settings.releases.current`; `lines.effective_release()` takes the maximum of current and one plus the highest integer line cut. `lines.cut_state()` looks only for that integer and prevents another open release line. `lineverbs.check_ready()` accepts digits only and cuts a release line from the integration tip after its members close. `target_of()` otherwise sends ordinary goals to integration. Those assumptions make a dotted target invalid and also make an earlier inserted patch unreachable or contaminated by later-release work. Hotfix lines already branch from production and propagate back to integration and an open release, but hotfixes use separate names/semantics and should not be silently substituted for a numbered target release.

## Approach

1. Introduce one release-identity parser/comparator shared by settings and goal validation, CLI, ledger/summaries, scheduling, dependency checks, line membership and release routing. Accept existing positive integer JSON numbers (not booleans or floats) and dotted strings of non-negative decimal integer components with a positive first component. Canonicalize component integers, discard only redundant trailing zero components, preserve internal zeros, and compare integer tuples padded with zeros: `2`, `2.0` and `2.0.0` canonicalize to `2`; `2.01` canonicalizes to `2.1`; `2 < 2.0.0.1 < 2.0.1 < 2.1 < 2.10 < 3`. Accept arbitrarily many finite components rather than a fixed version depth. No binary float conversion, raw string lexicographic comparison, or semantic-version prerelease/build metadata. Apply ordinary resource and platform Git-ref validation without introducing a fixed component-count limit. For existing stored integer releases, read and display their existing identity as today; newly written dotted values use canonical strings, with integer targets retaining their backward-compatible integer representation. Expose canonical identity consistently in diagnostics and JSON outputs, documenting the mixed legacy/new representations. A single canonical ref and idempotence/request key must make `release/2`, `release/2.0`, integer 2, and string `2.0` resolve to one line, never two branches.
2. Replace successor arithmetic with a portfolio of explicitly targeted release identities. Keep existing integer-only behavior and existing default assignment semantics for installations that have not opted into the feature; for dotted targets compute the ordered outstanding frontier from actual explicitly targeted goal records and line state, rather than synthesizing a floating-point successor or assuming a numeric next release exists. Insertion works at arbitrary finite depth, including targets between two already known dotted targets; numeric prefixes and internal zeros are identifiers, not evidence of Git ancestry. A target is identified by normalized equality for membership, dependencies, counters, human approvals and completion. Allow an owner to add or retarget an open goal to an earlier unclosed target explicitly, even after a later line was cut; do not rewrite other goal assignments. Detect an already finished canonical line or duplicate alias and refuse reuse. Later line state and existing work are never silently renumbered, reset, or auto-closed. Ensure dependencies and ordering cannot deadlock an inserted patch behind work explicitly targeting a later release; expose actual blockers rather than silently weakening gates.
3. Classify an explicitly inserted target as an isolated release line **before any member can start or merge**, whether a later target is only planned/uncut or already has a line. Record this mode and exact verified released base with the goal/line using canonical identity, and make `target_of`, frontier, worker dispatch, `git.base`, PR target and `integrate` refuse member delivery while the line is absent or its source cannot be verified; do not fall back to integration. The owner explicitly approves creation, including canonical ID and exact historical base. Derive the base from recorded released provenance and Git ancestry, never from a syntactic fixed-depth prefix, and show the owner the immutable SHA, source release and current production tip. For example, `2.0.0.1` and then `2.0.1` each use the appropriate actually released baseline. If any member was already completed against integration before classification, detect that from checkpoint/merge/target provenance and block line activation rather than treating it as present: retain its history and require an explicit reviewed backport/new or reopened work item on the isolated line, or report a human resolution; never rewrite or cherry-pick it silently. Detect in-flight work and retarget races via goal/line records and leases; require a fresh target/base check on dispatch, before PR creation and integration, and reject attempts observed to be stale, preserving their work for review. These checks cannot atomically observe separate remote refs and do not eliminate the final check-to-merge race described below. Apply this isolation even when later release 3 is not cut but its work already reached integration.
4. Bind creation to the owner-approved **immutable source SHA** and its recorded release evidence, not to a moving source label. A goal-record CAS plus independent ref reads is not a cross-ref transaction. The post-create `verified` state means only those refs were observed matching the approved snapshot; it does not certify they stayed unchanged. If production or source-goal provenance changes after the final read, the isolated patch line can still advance provisionally and remains isolated pending refreshed review. A destination CAS compares only that destination, not production or a source-goal ref.

   Before dispatch/base/PR and before promotion or forward-port, re-fetch recorded target identity, exact immutable source evidence, mode, patch head, production/destination and goal records. If a mismatch is observed, stop and require fresh review/approval or explicit recovery; preserve provisional patch work. Bind the owner approval to the snapshot and exact PR head. Deliver using the repository’s normal GitHub pull-request workflow: required reviews, checks, merge queue and branch rules apply; use the supported expected-PR-head guard (`--match-head-commit`/`expectedHeadOid`) when merging. Do not bypass branch protection or require a special live-source cross-ref transaction in this delivery. Ordinary expected-head checking does **not** atomically verify an independent source-goal ref or expected destination/base SHA. Source provenance is the approved immutable snapshot, not a live revocation guarantee: a change after the final check can race the merge. Independently, a permitted direct update of an unprotected patch-line ref may use the existing expected-old-SHA destination guard; it must never be used to bypass required PR protection.

   Record the source snapshot and last observed base, then after the protected PR merge record the actual merge commit/base and re-read source provenance. If the base or source changed between final preflight and the merge, the merge may already have happened; mark it for human review, stop automatic subsequent propagation or completion, retain the evidence, and do not claim it was atomically prevented or automatically undo it. If a mismatch is known before merge, do not merge: obtain fresh preview and approval. Where the provider cannot prove the actual base after a merge, report that evidence limitation rather than claiming equality. An external source move away and back to the same SHA between observations is not audited by this workflow. A stricter live-source or destination cross-ref guard belongs to a future goal and is not a selectable mode or requirement here.
5. Give inserted lines a recorded `inserted` mode with `production_patch` versus isolated `maintenance` finish targets. In this mode pre-`approve_finish` `git.line_sync` records the exact patch tip but does not merge into integration, production or later release lines. Approval shows exact patch head, immutable source snapshot, last observed destination and proposed propagation targets. For a current-production patch, use GitHub’s protected PR merge with its required reviews/checks and expected PR head; recheck the base and source before invoking it, but honestly expose that no expected-base or independent-source atomic comparison is provided by that API. If the precheck finds production advanced, stop for refreshed approval. If it advances in the final check-to-merge window, the PR can merge into the newer base: inspect and record the actual merge result, pause subsequent automation and seek review; do not force push, roll back or pretend the merge failed to occur. After a successful reviewed finish, forward-port to integration and eligible later lines via their normal protected PRs, each with its own source/head approval, known-mismatch precheck and the same disclosed race limitation; report partial state. An older maintenance release finishes on its isolated retained release line without moving the main production branch; forward-port is separately approved. Serialize engine-controlled work with existing leases without claiming they serialize outside GitHub pushes. Preserve arbitrary-depth canonical IDs and existing integer behavior; without branching report the isolated-line prerequisite.
6. Implement as a named engine capability required by a reviewed policy update before any writer produces dotted strings, a dotted `flow.name` at any depth, new line state, or modified ledger/trailers. No old writer may truncate or misinterpret an internal zero component. Old engines must refuse writes on the upgraded policy, not ignore unknown targets or sort them numerically incorrectly. Preserve old goals, policy numeric fields, existing branch names and commit histories; no wholesale rewrite is needed. Before activation, inspect already-existing remote release refs and line records for alias collisions or noncanonical names. A collision is a surfaced blocker requiring explicit owner resolution, not an automatic rename or force push. Document upgrade order, staged policy adoption, rollback constraints once dotted state exists, and how custom workflows/branches adopt the new behavior; unrelated broken migration mechanisms are a separate goal.

## Concrete CLI, approval and compatibility contracts

Follow the existing `release cut N --answer F` and `hotfix start X --answer F` pattern while distinguishing early inserted-line creation from cutting a completed ordinary release:

- `zzzops release insert <TARGET> --from <SOURCE_RELEASE>` is a read-only preview when `--answer` is absent. Both identifiers use the same dotted parser and canonicalization. It requires the reviewed capability and branching policy described below. It does not change refs, create a goal, reserve a lease, or trigger delivery. Its JSON contains `insert_preview` with `target`, `source_release`, `source_goal` (the unique completed release-line goal), `source_commit` (the immutable full Git SHA proven by the successfully finished source line's release-provenance record: `production_merge` for a production release, or its owner-approved exact line tip for an isolated maintenance release), `source_provenance_kind` and `source_provenance_goal_commit`, `production_ref`, `production_commit` (the freshly read full SHA), `mode` (`production_patch` or `maintenance`), `branch`, `later_lines`, `already_completed_members`, and `fingerprint` (a stable hash over all of these approval-bearing fields). It also contains `answer_template` with `decision`, `quote`, `decided_by`, and `fingerprint`. The preview makes no irreversible choice on the owner's behalf; it reports ambiguity, missing history, ref/alias collisions, unsafe branch rules and already-completed members as explicit blockers rather than inventing a baseline. An unbranched policy reports the existing branching prerequisite.
- `zzzops release insert <TARGET> --from <SOURCE_RELEASE> --answer <F>` validates an answer with `decision: "approved"`, nonempty verbatim `quote` and `decided_by`, and the exact preview `fingerprint`. Its source is the immutable full `source_commit` captured in the preview, not a moving remote ref, and it verifies the named source goal is closed successfully and its current finish record resolves to immutable approved release provenance, with Git ancestry and commit existence verified. For a normal production line use the successful finished `production_merge` SHA; for an isolated maintenance line use the exact SHA recorded in the successful finish record and bound to its owner-approved `line_sync` head. A numeric label, an open/unapproved line, the mutable current release ref, or a claimed but absent SHA is not proof. When the recorded finished source is missing or cannot prove ancestry, stop and request explicit source-history recovery; do not infer from a numeric prefix, newest branch or Git tag. `source_release` is an existing completed release, not a raw SHA; requiring it makes nested backports reviewable. To insert `2.0.0.1` after finished release `2`, use `--from 2` regardless of textual nesting. A source on which a target was not based cannot be silently reinterpreted later.
- Before line creation, re-read the goal/source records, branch aliases and production and recompute the preview fingerprint; a known change requires a new preview and approval. Atomically create the canonical line ref and its goal in `pending_verification` from the approved immutable source SHA only if both destination refs are absent. This transaction does not compare independent production or source-goal refs. Re-read the created line, production and source records; observed mismatch leaves the line pending and requires refreshed review. Matching observations allow a goal-record CAS to record `verified` as an observed snapshot only. A production/source move after those reads can escape that goal-only CAS and permit speculative isolated work, including provisional patch-line advancement; it is not a cross-ref guarantee. Subsequent known mismatches block merge and require fresh approval. PR merge retains normal GitHub protections and expected head; it has no atomic source/base assertion. The successful merge result and subsequent checks must report any discovered race and pause downstream actions, without silently rewriting history. Retry aliases recover one canonical line and mismatched/stale answer fingerprints refuse.
- `mode` is `production_patch` when the approved source commit is the observed production tip. An older source can be `maintenance` when its provenance and the current production release have a verified common released ancestor; a prior isolated maintenance tip need not itself be an ancestor of production. Verify the recorded source lineage and current observed production, block unprovable/unrelated ancestry, and never move main production as part of maintenance finish. Revalidate before finishing, bind the result to owner approval, and use protected PRs with the disclosed expected-head and cross-ref limitation for any approved forward-port. A mode change known before merge requires renewed approval; one occurring after the final read can race the merge and must be reported if discovered. Completed members already on integration retain their history and require separately reviewed backport/reopen work.
- The capability name is `insertable_release_targets`, defined by `engine/capabilities/insertable_release_targets.txt`. Install/upgrade every engine writer first; then a separately reviewed policy change adds `"insertable_release_targets"` to `settings.engine.requires`. Until that policy is in effect, the engine rejects `release insert` and non-integer new target writes and preserves the current integer-only behavior, including any legacy read-only diagnostics. Once it is required, pre-capability engines refuse writes using the existing `engine_too_old` guard before touching goal, lease, line or production refs. Capability activation itself does not migrate, rename or create branches, and aborts if existing line/ref aliases collide under canonicalization. Project policy/workflow updates remain reviewed and may be previewed with the existing policy tools. Refusal of unsafe/unknown mixed writers is a requirement, not a claim the old engine understands dotted labels.

**Maintenance provenance and nested targets.** The opt-in inserted-line graph records a distinct successful maintenance finish outcome with the exact approved line tip, source goal/release and immutable source SHA, the exact `line_sync` subject/approval reference and finish mode. This is a ZzzOps logical release-line completion, not proof of external deployment or publication. A normal production release continues to expose its legacy `production_merge`; do not fabricate a production merge SHA for maintenance to satisfy the old schema. Add the necessary capability-gated optional finish result/graph schema without rewriting old completed records. To use finished `2.1` as source for `2.1.1` after production advances to `3`, validate that `2.1` is closed `done`, its finish and exact-tip approval are current, its recorded tip descends from its own recorded released source, and those immutable commits are present. Resolve `source_commit` from that approved recorded tip, never today’s movable `release/2.1` ref. Verify the production line and maintenance history share the earlier recorded released base, display both provenances and mode in the preview, and keep the new line isolated. Missing, unapproved, reopened, stale, ambiguous, unreachable or rewritten provenance is a blocker; do not guess or claim deployment. Capability activation/mixed-version safeguards apply to new finish result schemas as well as new identifiers.

These names and fields deliberately align with the existing CLI's `release` namespace, answer-file and branching settings; preserve existing `release cut <integer> --answer <F>` behavior. `next` surfaces a matching owner item when an inserted target needs a verified line and prints the preview command. `new --file`, `edit`, `next`, `show`, `validate`, `release cut` and line finish normalize aliases consistently; never encode numeric identifiers as JSON floats. Do not change unrelated releases, infer Git ancestry from dotted labels, deploy or publish.

## Separate post-finish maintenance forward-port

Finishing an isolated maintenance line is complete when its owner-approved exact tip and source provenance are recorded and the retained release line is closed; it does not wait for, create, or move main production or integration. The finished record remains usable immediately as the immutable source for a nested maintenance target. A later forward-port is an optional, separately tracked operation, never an implicit phase of the closed source goal.

- `zzzops release forward-port <SOURCE_RELEASE> --to <DESTINATION>` is the explicit request to start or resume one forward-port. Canonicalize `<SOURCE_RELEASE>` and resolve a unique closed-successful maintenance line with a current approved finish, its finish record's exact immutable line tip, and its released-source lineage. `<DESTINATION>` is an exact Git branch, limited to the configured integration branch, configured production branch, or an existing open release line; reject the closed source branch, internal `zzzops/` refs, missing/ambiguous/unsafe destinations and destinations not descended from the previously verified common release ancestor. Production may be a newer branch: a reviewed forward merge must advance it without rewinding; this never means replacing production with the older maintenance branch. Starting a forward-port is an explicit request, not permission to merge or deploy. If source proof is missing, unapproved, stale or contradictory, stop and show the recovery context instead of using the current mutable source-line ref.
- Create a separate durable forward-port goal using a dedicated customizable `forward_port` graph and a deterministic request key derived from the canonical source goal ID, exact approved source tip and exact destination branch. Capture the source goal commit, finish/approval fingerprint and source tip, destination branch and last observed tip, operation mode and request key. Atomically allocate the new goal and a uniquely named temporary `zzzops/forward/<goal-id>` PR head at the exact source tip using conditional ref creation. This branch is only a carrier: never modify the source release line or change its closed record. A repeated command with the same key returns the existing operation and its `next` action, including after partial completion; it must not create another PR or silently choose a new source. A changed source provenance or a different destination is a new explicit request, subject to eligibility checks. Initial ref/goal races are handled with the engine's normal idempotent atomic push/CAS behavior.
- The prepare operation creates or reuses a GitHub pull request from that carrier head to the chosen destination, preserving branch protections, required checks and ordinary review. It records the PR number/URL, immutable PR head and observed destination base; it does not merge. `zzzops next --goal <forward-goal>` presents a separate human approval for the concrete PR, displaying the closed source release and exact approved finished tip, target branch and observed base SHA, PR URL/head, and the cross-ref limitation. Approval explicitly covers this forward-port only and does not approve a different destination, source, head, or later changed preview. No duplicate human approval is inferred from the earlier maintenance finish.
- After that approval, the graph's merge operation rechecks source-goal provenance, destination/PR head and branch eligibility and refuses known differences, asking for fresh review when needed. Merge through the repository's protected PR workflow using the supported expected PR head; never use a force update, bypass GitHub review/checks, or claim an atomic compare of an independent source-goal or destination ref. A changed destination or source between the final check and GitHub merge can race this API; inspect and persist actual PR result, merge commit/base and source evidence, stop downstream automation and surface a human review if divergence is found. Conflicts, failed checks, permission errors, protected-branch restrictions or unsupported ref operations leave the forward-port goal resumable and do not alter the closed maintenance goal. Preserve an already merged PR as a recorded outcome, never attempt to unmerge or silently repeat it.
- Persist per-operation lifecycle and partial state as engine records: source goal/ref snapshot, exact source tip, PR/head, observed destination/base, approval fingerprint, merge outcome/actual merge commit and divergence or conflict details. The `next`/retry path can resume after a crash or partial GitHub response by inspecting the recorded operation and actual PR state. Successful completion closes only the forward-port goal; remove its temporary branch with expected-head safety only after verifying the PR result and policy permits cleanup. There is one explicit approval per destination and no automatic cascading to other branches. A second destination is a separate request/goal and review. This is release-branch coordination, not package publishing or deployment. Capability-gate the new graph/schema and CLI under the same reviewed `insertable_release_targets` activation; older writers must refuse before mutation.

### Forward-port when GitHub reports no diff

Before creating a PR, and after any provider “no commits between”/no-diff refusal or an uncertain create/merge response, fetch the exact current destination SHA and inspect actual Git ancestry plus existing PRs for the same destination and immutable source/head. Do not loop on PR creation, infer success from the error text, reopen or alter the closed maintenance goal, or mark an unobserved merge as completed. Outcomes are evidence-specific:

- If the exact recorded source tip is an ancestor of the fetched destination tip, present `already_in_history` with source SHA, observed destination SHA and proof `git merge-base --is-ancestor <source> <destination>`. This proves historical reachability only, not that a subsequent revert or other change has left the same behavior in the destination.
- If the provider records a matching already-merged PR, verify its base branch, recorded exact approved head SHA, actual merge commit and that this merge commit is an ancestor of the observed destination tip. Present `previously_merged` with the PR link, head, merge SHA, observed destination SHA and proof. This records a provider-observed merge, including squash/rebase cases where the original source is not an ancestor; it does not claim the changes are still effective after later reverts. Do not create another PR or claim a new merge was performed.
- If neither condition is verifiable—including equal trees or equivalent-looking diffs with divergent ancestry, ambiguous or unavailable PR history, deleted/missing objects, or a provider no-diff response with no provable integration—retain the resumable operation in a clear `no_diff_unproven` block showing the exact available SHAs/provider evidence. Ask for investigation or a fresh explicit plan; do not synthesize merge records, mutate source/destination or repeatedly create PRs. Never assume a cherry-pick equivalence from equal trees alone.

For either evidence-backed non-mutating outcome, present the human with the concrete evidence and its limitations under the same separate forward-port approval; the approval fingerprint binds source goal/provenance, immutable source SHA, observed destination SHA, evidence kind and relevant PR/merge SHA. On approval, re-read the source record and destination; any observed change requires a new evidence preview and approval. Record the outcome as `already_in_history` or `previously_merged`, not `merged`, and close only the forward-port goal. There is no new PR merge and no bypass of branch protections or required checks; an existing provider PR is reported as historical evidence only. The recorded outcome is an observation of those exact Git objects, not a claim that an independent destination/source ref could not have moved after the last read or that contents will stay present; the accepted GitHub cross-ref limitation still applies. Any temporary carrier branch may be removed only under the existing expected-head cleanup rules, and the closed maintenance record remains untouched. If the operation had already recorded its own successful merge before a retry, recover that recorded/provider-verified result first; do not relabel it as a fresh no-op.

## Scope and risks

Goal target labels and release-branch workflow only; semantic-version calculation, tags, package publishing, deployment, automatic production promotion, and unrelated migration repairs remain out of scope. Patch isolation must be proven from actual Git ancestry, not a label; alias canonicalization must precede storage, membership and ref operations; and empty/legacy portfolios must not lose their current behavior. Concurrent release lines and partial propagation are the highest-risk cases and require real Git/remote tests.
