# Insertable dotted target releases

## Outcome

A repository can target an ordered patch such as `2.1` even after `3` has been cut, without renumbering or implicitly reassigning goals already targeting `3`. `2`, `2.0` and `2.0.0` identify one target; `2.1` and `2.10` remain distinct and sort numerically by components. Identifiers have arbitrarily many finite numeric components: `2 < 2.0.0.1 < 2.0.1 < 2.1`, allowing further targets to be inserted between existing targets. A patch line can be based on the released code and delivered without including work from an unrelated later release. Existing approvals and release-line finish gates still apply; ZzzOps does not publish a package or deploy anything.

## Current behavior

At integration commit `cb33c2d`, `schemas.py` accepts only integer `goal.release` and `settings.releases.current`; `lines.effective_release()` takes the maximum of current and one plus the highest integer line cut. `lines.cut_state()` looks only for that integer and prevents another open release line. `lineverbs.check_ready()` accepts digits only and cuts a release line from the integration tip after its members close. `target_of()` otherwise sends ordinary goals to integration. Those assumptions make a dotted target invalid and also make an earlier inserted patch unreachable or contaminated by later-release work. Hotfix lines already branch from production and propagate back to integration and an open release, but hotfixes use separate names/semantics and should not be silently substituted for a numbered target release.

## Approach

1. Introduce one release-identity parser/comparator shared by settings and goal validation, CLI, ledger/summaries, scheduling, dependency checks, line membership and release routing. Accept existing positive integer JSON numbers (not booleans or floats) and dotted strings of non-negative decimal integer components with a positive first component. Canonicalize component integers, discard only redundant trailing zero components, preserve internal zeros, and compare integer tuples padded with zeros: `2`, `2.0` and `2.0.0` canonicalize to `2`; `2.01` canonicalizes to `2.1`; `2 < 2.0.0.1 < 2.0.1 < 2.1 < 2.10 < 3`. Accept arbitrarily many finite components rather than a fixed version depth. No binary float conversion, raw string lexicographic comparison, or semantic-version prerelease/build metadata. Apply ordinary resource and platform Git-ref validation without introducing a fixed component-count limit. For existing stored integer releases, read and display their existing identity as today; newly written dotted values use canonical strings, with integer targets retaining their backward-compatible integer representation. Expose canonical identity consistently in diagnostics and JSON outputs, documenting the mixed legacy/new representations. A single canonical ref and idempotence/request key must make `release/2`, `release/2.0`, integer 2, and string `2.0` resolve to one line, never two branches.
2. Replace successor arithmetic with a portfolio of explicitly targeted release identities. Keep existing integer-only behavior and existing default assignment semantics for installations that have not opted into the feature; for dotted targets compute the ordered outstanding frontier from actual explicitly targeted goal records and line state, rather than synthesizing a floating-point successor or assuming a numeric next release exists. Insertion works at arbitrary finite depth, including targets between two already known dotted targets; numeric prefixes and internal zeros are identifiers, not evidence of Git ancestry. A target is identified by normalized equality for membership, dependencies, counters, human approvals and completion. Allow an owner to add or retarget an open goal to an earlier unclosed target explicitly, even after a later line was cut; do not rewrite other goal assignments. Detect an already finished canonical line or duplicate alias and refuse reuse. Later line state and existing work are never silently renumbered, reset, or auto-closed. Ensure dependencies and ordering cannot deadlock an inserted patch behind work explicitly targeting a later release; expose actual blockers rather than silently weakening gates.
3. Classify an explicitly inserted target as an isolated release line **before any member can start or merge**, whether a later target is only planned/uncut or already has a line. Record this mode and exact verified released base with the goal/line using canonical identity, and make `target_of`, frontier, worker dispatch, `git.base`, PR target and `integrate` refuse member delivery while the line is absent or its source cannot be verified; do not fall back to integration. The owner explicitly approves creation, including canonical ID and exact historical base. Derive the base from recorded released provenance and Git ancestry, never from a syntactic fixed-depth prefix, and show the owner the immutable SHA, source release and current production tip. For example, `2.0.0.1` and then `2.0.1` each use the appropriate actually released baseline. If any member was already completed against integration before classification, detect that from checkpoint/merge/target provenance and block line activation rather than treating it as present: retain its history and require an explicit reviewed backport/new or reopened work item on the isolated line, or report a human resolution; never rewrite or cherry-pick it silently. Detect in-flight work and retarget races via goal/line records and leases; require a fresh exact target/base check on dispatch, before PR creation and integration, and reject stale attempts, preserving their work for review. Apply this isolation even when later release 3 is not cut but its work already reached integration.
4. Bind creation to the owner-approved **immutable source SHA** and source-release evidence, not to a moving production label. Git cannot generally atomically compare multiple unchanged remote refs while CAS-updating only a goal: a fetch followed by a goal-ref CAS is not a remote snapshot transaction, and pushing unchanged refs or engine-controlled leases must not be treated as one. The post-create `verified` record below means only “these exact refs were observed with this immutable approved source”; it is **not** a durable guarantee that external writers have not moved production or the line since. A concurrent external production or source-goal change after the last observation may allow a worker to start and also advance the isolated patch-line ref as provisional work: a CAS on the patch-line destination does not compare a different production or goal ref. The ref remains isolated and must not be treated as a finished or promotable release until the source and destination have been freshly checked and explicitly approved. Do not claim that a goal-only CAS, nor a destination-only CAS, detects a change to another ref.

   Before dispatch/base/PR and again before any mutation, re-fetch and compare recorded target identity, immutable source provenance, current mode, actual line tip, current production tip and relevant goal records. A known mismatch blocks work and requires fresh preview/approval or reviewed recovery. An undetectably racing production or source-goal mismatch after a read can leave speculative commits both in a work ref and on the isolated patch-line ref: a patch-line expected-old-SHA check may still succeed if only the other ref changed. Such patch-line advancement is explicitly provisional, visible and retained for review; it does not authorize production, integration or any forward-port update. Every actual patch-line, production or forward-port ref update must atomically compare the exact expected old SHA **on that destination ref as part of its real remote update** (e.g. an atomic fast-forward Git push with an expected-old-value lease; first verify candidate descendant of expected SHA). A plain pre-read, unchanged no-op push, internal lease, goal-only CAS, or `gh pr merge --match-head-commit` head check is not a destination compare-and-swap. Re-read before dispatch is diagnostic, not a substitute for this guard. On a protected branch/provider that permits only PR merges and has no atomic expected-base compare, stop and report the unsupported safety condition; never bypass protection or silently rely on best-effort checking. Before production promotion or any forward-port, obtain a fresh exact owner-approved snapshot binding the patch head, immutable source provenance including the source-goal record, destination, and expected old target. Re-fetch and block known mismatches; a destination-only CAS catches only a changed destination, not a concurrently revoked source goal. Where policy requires source provenance to remain live through the remote update, require a real server-side transaction that atomically verifies that source-goal SHA and updates the expected destination SHA together; if unavailable, stop rather than silently pretend the source check is atomic. A local bare-Git adapter may use a real `git update-ref --stdin` transaction with `verify` on source and `update` on destination; a hosted provider must prove equivalent semantics or refuse this operation, and ordinary no-op pushes or `--match-head-commit` are not proof. The release ref and immutable provenance are never rewritten to hide a race.

   This protects against externally changed target refs at the actual Git write linearization point, not against an external actor moving a ref away and back to the same SHA between observations. If the ref moves away and back, the guarded update's old value and approved Git content are again identical; do not claim a complete external-ref movement audit. For patches where production changed after initial line preview, stop automatic production promotion and request a refreshed mode/source preview and approval; immutable-base speculative work remains isolated. Test deterministic remote updates after the final read but before goal CAS, after dispatch checks but before patch-line push, and after finish approval but immediately before production push. Record whether only work refs changed or the isolated patch line also advanced provisionally; prove no unapproved production/forward-port mutation or rollback occurred. Git history and current exact values, not labels alone, determine the source and approved targets.
5. Give inserted lines their own recorded `inserted` mode in the configured release graph, with clear `current-production` versus isolated `maintenance` finish targets. Update the graph and `git.line_sync`: for this mode, pre-`approve_finish` sync records/validates the exact line tip but does **not** merge into integration, production or any later release. Approval presents the exact line head, source, finish target and any proposed forward-propagation destinations. A current-production patch may move production only after owner approval and a checked fast-forward merge whose expected target SHA is enforced atomically by the remote; if production advanced, the compare fails and approval must be refreshed. Verify the candidate is a descendant of the expected production SHA, so any lease guard cannot authorize a rewind. Do not bypass branch protection to gain atomicity; where the provider cannot guarantee the required target comparison, stop for a supported protected-branch/owner flow. Only after a successful authorized finish may the operation forward the approved patch to integration and relevant open later lines, each with explicit per-target eligibility, exact-head/CAS guards, visible partial state and reviewed conflicts. Never use a stale head or overwrite a later line. For an **older maintenance release after production has advanced**, finish the isolated retained release line without changing the main production branch or silently merging it backwards; any optional forward-port is a separately explicit reviewed action and never implies deployment. Already-cut/closed target aliases remain protected from duplicate lines. Serialize engine-controlled operations via existing leases and idempotent compare-and-set, but do not pretend those leases serialize external Git pushes. Preserve full canonical components in ref names, flow state and collision checks at arbitrary depth; no fixed-depth naming assumptions. For policies without branching, support identity/ordering but report the need for a suitable isolated line rather than claiming safe parallel patch delivery.
6. Implement as a named engine capability required by a reviewed policy update before any writer produces dotted strings, a dotted `flow.name` at any depth, new line state, or modified ledger/trailers. No old writer may truncate or misinterpret an internal zero component. Old engines must refuse writes on the upgraded policy, not ignore unknown targets or sort them numerically incorrectly. Preserve old goals, policy numeric fields, existing branch names and commit histories; no wholesale rewrite is needed. Before activation, inspect already-existing remote release refs and line records for alias collisions or noncanonical names. A collision is a surfaced blocker requiring explicit owner resolution, not an automatic rename or force push. Document upgrade order, staged policy adoption, rollback constraints once dotted state exists, and how custom workflows/branches adopt the new behavior; unrelated broken migration mechanisms are a separate goal.

## Concrete CLI, approval and compatibility contracts

Follow the existing `release cut N --answer F` and `hotfix start X --answer F` pattern while distinguishing early inserted-line creation from cutting a completed ordinary release:

- `zzzops release insert <TARGET> --from <SOURCE_RELEASE>` is a read-only preview when `--answer` is absent. Both identifiers use the same dotted parser and canonicalization. It requires the reviewed capability and branching policy described below. It does not change refs, create a goal, reserve a lease, or trigger delivery. Its JSON contains `insert_preview` with `target`, `source_release`, `source_goal` (the unique completed release-line goal), `source_commit` (the immutable full Git SHA proven by the successfully finished source line's release-provenance record: `production_merge` for a production release, or its owner-approved exact line tip for an isolated maintenance release), `source_provenance_kind` and `source_provenance_goal_commit`, `production_ref`, `production_commit` (the freshly read full SHA), `mode` (`production_patch` or `maintenance`), `branch`, `later_lines`, `already_completed_members`, and `fingerprint` (a stable hash over all of these approval-bearing fields). It also contains `answer_template` with `decision`, `quote`, `decided_by`, and `fingerprint`. The preview makes no irreversible choice on the owner's behalf; it reports ambiguity, missing history, ref/alias collisions, unsafe branch rules and already-completed members as explicit blockers rather than inventing a baseline. An unbranched policy reports the existing branching prerequisite.
- `zzzops release insert <TARGET> --from <SOURCE_RELEASE> --answer <F>` validates an answer with `decision: "approved"`, nonempty verbatim `quote` and `decided_by`, and the exact preview `fingerprint`. Its source is the immutable full `source_commit` captured in the preview, not a moving remote ref, and it verifies the named source goal is closed successfully and its current finish record resolves to immutable approved release provenance, with Git ancestry and commit existence verified. For a normal production line use the successful finished `production_merge` SHA; for an isolated maintenance line use the exact SHA recorded in the successful finish record and bound to its owner-approved `line_sync` head. A numeric label, an open/unapproved line, the mutable current release ref, or a claimed but absent SHA is not proof. When the recorded finished source is missing or cannot prove ancestry, stop and request explicit source-history recovery; do not infer from a numeric prefix, newest branch or Git tag. `source_release` is an existing completed release, not a raw SHA; requiring it makes nested backports reviewable. To insert `2.0.0.1` after finished release `2`, use `--from 2` regardless of textual nesting. A source on which a target was not based cannot be silently reinterpreted later.
- Immediately before the atomic push, re-read the goal and source records, branch aliases and production ref and recompute the preview fingerprint. If any approval-bearing input changed, refuse with `preview_stale`, show the fresh preview and request a fresh answer. The atomic push creates the canonical inserted `release/<TARGET>` line and its goal in `pending_verification` state from exactly `source_commit`, only if both destination refs are absent; it cannot claim atomicity over external updates to production. Re-read production and the created line after push; if those observations differ, leave the line `pending_verification` and surface a new preview/approval or conflict recovery. If they match, CAS-update the goal record with the observed exact values and mark it `verified` as an observed snapshot, not a cross-ref transaction or a promise the remote remained unchanged between the reads and CAS. Members cannot run while the record is pending; after verification, a direct external move in the read-to-CAS window may escape that observation. Subsequent checks may block the member before start, or a member may do speculative work on the recorded immutable base and provisionally advance the isolated patch line. A patch-line write atomically checks that line's expected old value, so it must fail if the patch-line destination differs but may succeed if only production or the source-goal ref moved. Before any production or forward-port action, refresh and approve the exact source/production snapshot and enforce the stronger destination and, where required, source-provenance transaction guards in step 4. Never report “no worker started” as a guarantee for this unprotected window. A separate owner answer to the refreshed preview verifies the unchanged original source SHA and updates the recorded production SHA/mode; it never silently creates a second branch or rewrites a ref. Repeated identical successful submissions recover the same canonical line; a mismatched answer or alias returns a refusal, not a second identity. If goal metadata changes concurrently, CAS fails and re-preview is required.
- `mode` is `production_patch` only when the approved source commit is the current production tip. An older source can be `maintenance` when its source provenance and the current production release have a verified shared released ancestor; for a prior isolated maintenance line its approved tip need not itself be an ancestor of production, because that maintenance branch was intentionally never merged there. Require the recorded source lineage to prove a common released base reachable from both the maintenance tip and current production, and ensure target/source release identity and recorded history are consistent; unprovable or unrelated ancestry blocks. The main production ref is never moved as part of a maintenance finish. This decision is bound into the answer fingerprint, revalidated on the remote before the finish, and never silently changed. Production finish and each authorized forward-port use the graph's exact-head approval and the guarded atomic destination checks described above. Old completed members found on integration keep their records; they are not treated as patch members on the new line and require separately reviewed backport/reopen work. No old goal is rewritten or automatically cherry-picked by insertion.
- The capability name is `insertable_release_targets`, defined by `engine/capabilities/insertable_release_targets.txt`. Install/upgrade every engine writer first; then a separately reviewed policy change adds `"insertable_release_targets"` to `settings.engine.requires`. Until that policy is in effect, the engine rejects `release insert` and non-integer new target writes and preserves the current integer-only behavior, including any legacy read-only diagnostics. Once it is required, pre-capability engines refuse writes using the existing `engine_too_old` guard before touching goal, lease, line or production refs. Capability activation itself does not migrate, rename or create branches, and aborts if existing line/ref aliases collide under canonicalization. Project policy/workflow updates remain reviewed and may be previewed with the existing policy tools. Refusal of unsafe/unknown mixed writers is a requirement, not a claim the old engine understands dotted labels.

**Maintenance provenance and nested targets.** The opt-in inserted-line graph records a distinct successful maintenance finish outcome with the exact approved line tip, source goal/release and immutable source SHA, the exact `line_sync` subject/approval reference and finish mode. This is a ZzzOps logical release-line completion, not proof of external deployment or publication. A normal production release continues to expose its legacy `production_merge`; do not fabricate a production merge SHA for maintenance to satisfy the old schema. Add the necessary capability-gated optional finish result/graph schema without rewriting old completed records. To use finished `2.1` as source for `2.1.1` after production advances to `3`, validate that `2.1` is closed `done`, its finish and exact-tip approval are current, its recorded tip descends from its own recorded released source, and those immutable commits are present. Resolve `source_commit` from that approved recorded tip, never today’s movable `release/2.1` ref. Verify the production line and maintenance history share the earlier recorded released base, display both provenances and mode in the preview, and keep the new line isolated. Missing, unapproved, reopened, stale, ambiguous, unreachable or rewritten provenance is a blocker; do not guess or claim deployment. Capability activation/mixed-version safeguards apply to new finish result schemas as well as new identifiers.

These names and fields deliberately align with the existing CLI's `release` namespace, answer-file and branching settings; preserve existing `release cut <integer> --answer <F>` behavior. `next` surfaces a matching owner item when an inserted target needs a verified line and prints the preview command. `new --file`, `edit`, `next`, `show`, `validate`, `release cut` and line finish normalize aliases consistently; never encode numeric identifiers as JSON floats. Do not change unrelated releases, infer Git ancestry from dotted labels, deploy or publish.

## Test strategy

- Exercise parser and comparison properties for arbitrarily nested finite identifiers, including `2 < 2.0.0.1 < 2.0.1 < 2.1`, further insertions between adjacent already-known targets, aliases (`2.0.1.0` = `2.0.1`, `2.0` = `2`), preservation of internal zeros, deep canonical branch/ref round-trips and `2.1` vs `2.10`; also cover invalid floats/booleans/negative or malformed strings, ref safety, bounded components, canonical JSON/CLI/trailer round-trips, legacy integer policy/goals and collision detection. Test duplicate cuts/retries across alternate spellings produce one goal/ref.
- Real isolated Git remote fixtures: create a production release 2, cut release 3 and retain unreleased work on its line, then insert `2.1` from the verified production 2 base. Separately insert and deliver nested `2.0.0.1` before a cut `2.0.1` and `2.1`, verifying the source baseline by recorded Git ancestry and forwarding the patch without contaminating later lines. Merge patch goals to 2.1 and prove its tree excludes 3-only work, finish only after approval, and verify patch propagation to production, integration and 3 while preserving 3 content and assigned goals. Cover conflicts, racing creation, partial failures, stale refs, exact-head approval, already-advanced production, held/closed/dependency states and no-branch policies. Demonstrate ordinary integer release workflows remain unchanged.
- Exercise existing later-only commits already on integration with the later target uncut and cut; an inserted patch must remain based on its independently verified baseline. Race explicit insertion/retarget with worker dispatch and integration, including an already completed member on integration: no member is silently delivered to the wrong branch or falsely marked complete. Verify a retained work item is routed to explicit reviewed recovery.
- Real remote race fixtures move production after preview, between conditional line creation and verification, before a member dispatch, and immediately before finish. Verify pending lines do not dispatch; after an observed verification snapshot, if only production or source provenance changes, a patch-line update against an unchanged expected patch-line SHA may succeed as provisional isolated work. A change to the actual patch-line destination must make its expected-old-SHA update fail. Before production/forward-port, require refreshed exact source/target approval and the stated atomic guards; a production destination move must fail production CAS. Verify no unguarded check-then-push changes production and no stale write causes a rewind or wrong-base promotion. Include remote inability to atomically compare the destination and branch protection refusal.
- Assert inserted-mode `git.line_sync` records the exact patch head without changing integration, production, or later release refs before `approve_finish`; after approval, assert guarded propagation and safe partial failure. With production already at 3, create and finish an isolated 2.1 maintenance line from recorded release-2 ancestry, prove production remains on 3, and require separately approved forward-port.
- Drive the exact `release insert <TARGET> --from <SOURCE_RELEASE>` read-only preview and answer-file action in a real local Git remote: assert all approval-bearing fields and fingerprint, canonical alias idempotence and capability policy gating. Deterministically advance the remote production ref between preview, immediately-before-push, atomic line/goal creation and post-push verification. Check stale fingerprints/refusals and pending gating; inject an external move after final observation and before goal CAS. Verify an unchanged patch-line destination may still accept a provisional update while a changed patch-line destination rejects it; never infer changes to production/source-goal from the patch-line CAS. Verify no production/forward-port proceeds without the required refreshed approval and actual destination guard. Race source-goal metadata updates and two insert requests, and exercise source history missing/ambiguous, unsafe ancestry and completed members already on integration. The implementation must not pretend an atomic cross-ref check exists on a remote that cannot guarantee it.
- Finish `2.1` as an isolated maintenance line after production `3` without a production merge, retain its owner-approved exact line tip and source provenance, then preview/insert/deliver `2.1.1 --from 2.1`. Assert the preview selects that recorded tip even if the mutable `release/2.1` ref later moves, prove its common released base with production, and keep production on `3`. Exercise missing/changed goal records, stale approval, unclosed and unapproved lines, missing commits, unrelated histories and corrupt provenance; none may fall back to a numeric label or fabricate `production_merge`. Verify graph/schema/capability compatibility for both legacy and maintenance finish outcomes.
- Add deterministic hooks at final production/line read → goal CAS and dispatch pre-read → actual target update; a real remote writer changes production, source-goal provenance, or the target patch line separately in each gap. Goal CAS may succeed with a stale snapshot and a worker may start speculatively. If only production or source provenance changed, an otherwise valid patch-line CAS may succeed as provisional work; if the patch-line destination itself changed, its CAS must fail. Production/forward-port requires fresh source/target approval and its own actual guarded update; if live source revocation must also be enforced at the write linearization point, test a server-supported atomic verify-source/update-destination transaction and fail closed when the remote cannot provide one. Test provider without destination CAS, protected-branch failure, same-SHA no-op behavior and exact stale-preview recovery; do not assert an impossible cross-ref snapshot.
- Real bare-remote interleavings must distinguish which ref changes: (a) move production only just before an unchanged patch-line CAS and assert the line may advance provisionally, while production and all forward-port targets stay unchanged until reapproval; (b) revoke/change the source-goal approval only at that point and assert the same provisional result, then prove the refreshed review observes the revocation; (c) change the patch-line destination itself and assert its CAS fails; (d) after fresh promotion approval, move production before its update and assert production CAS fails. For policies requiring live source-provenance checks at promotion, use an actual local-server `git update-ref --stdin` transaction with `verify <source-goal-ref> <expected>` and `update <destination> <new> <expected>` to prove a source revocation immediately before commit rejects the whole operation. Also exercise a remote lacking equivalent cross-ref transaction support: promotion/forward-port must stop without changing any destination. Do not classify an unchanged ref or a goal-only CAS as a remote cross-ref guard.
- Exercise old/new writer combinations with the capability policy enabled and disabled; legacy readers must not silently mutate dotted state. Test activation refusal for alias collisions and no rewrite of existing histories. Run focused real-engine tests first, then existing integration/CLI tests and repository-required checks; do not contact or change real production branches.

## Scope and risks

Goal target labels and release-branch workflow only; semantic-version calculation, tags, package publishing, deployment, automatic production promotion, and unrelated migration repairs remain out of scope. Patch isolation must be proven from actual Git ancestry, not a label; alias canonicalization must precede storage, membership and ref operations; and empty/legacy portfolios must not lose their current behavior. Concurrent release lines and partial propagation are the highest-risk cases and require real Git/remote tests.
