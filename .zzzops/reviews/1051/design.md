# Insertable dotted target releases

## Outcome

A repository can target an ordered patch such as `2.1` even after `3` has been cut, without renumbering or implicitly reassigning goals already targeting `3`. `2`, `2.0` and `2.0.0` identify one target; `2.1` and `2.10` remain distinct and sort numerically by components. Identifiers have arbitrarily many finite numeric components: `2 < 2.0.0.1 < 2.0.1 < 2.1`, allowing further targets to be inserted between existing targets. A patch line can be based on the released code and delivered without including work from an unrelated later release. Existing approvals and release-line finish gates still apply; ZzzOps does not publish a package or deploy anything.

## Current behavior

At integration commit `cb33c2d`, `schemas.py` accepts only integer `goal.release` and `settings.releases.current`; `lines.effective_release()` takes the maximum of current and one plus the highest integer line cut. `lines.cut_state()` looks only for that integer and prevents another open release line. `lineverbs.check_ready()` accepts digits only and cuts a release line from the integration tip after its members close. `target_of()` otherwise sends ordinary goals to integration. Those assumptions make a dotted target invalid and also make an earlier inserted patch unreachable or contaminated by later-release work. Hotfix lines already branch from production and propagate back to integration and an open release, but hotfixes use separate names/semantics and should not be silently substituted for a numbered target release.

## Approach

1. Introduce one release-identity parser/comparator shared by settings and goal validation, CLI, ledger/summaries, scheduling, dependency checks, line membership and release routing. Accept existing positive integer JSON numbers (not booleans or floats) and dotted strings of non-negative decimal integer components with a positive first component. Canonicalize component integers, discard only redundant trailing zero components, preserve internal zeros, and compare integer tuples padded with zeros: `2`, `2.0` and `2.0.0` canonicalize to `2`; `2.01` canonicalizes to `2.1`; `2 < 2.0.0.1 < 2.0.1 < 2.1 < 2.10 < 3`. Accept arbitrarily many finite components rather than a fixed version depth. No binary float conversion, raw string lexicographic comparison, or semantic-version prerelease/build metadata. Apply ordinary resource and platform Git-ref validation without introducing a fixed component-count limit. For existing stored integer releases, read and display their existing identity as today; newly written dotted values use canonical strings, with integer targets retaining their backward-compatible integer representation. Expose canonical identity consistently in diagnostics and JSON outputs, documenting the mixed legacy/new representations. A single canonical ref and idempotence/request key must make `release/2`, `release/2.0`, integer 2, and string `2.0` resolve to one line, never two branches.
2. Replace successor arithmetic with a portfolio of explicitly targeted release identities. Keep existing integer-only behavior and existing default assignment semantics for installations that have not opted into the feature; for dotted targets compute the ordered outstanding frontier from actual explicitly targeted goal records and line state, rather than synthesizing a floating-point successor or assuming a numeric next release exists. Insertion works at arbitrary finite depth, including targets between two already known dotted targets; numeric prefixes and internal zeros are identifiers, not evidence of Git ancestry. A target is identified by normalized equality for membership, dependencies, counters, human approvals and completion. Allow an owner to add or retarget an open goal to an earlier unclosed target explicitly, even after a later line was cut; do not rewrite other goal assignments. Detect an already finished canonical line or duplicate alias and refuse reuse. Later line state and existing work are never silently renumbered, reset, or auto-closed. Ensure dependencies and ordering cannot deadlock an inserted patch behind work explicitly targeting a later release; expose actual blockers rather than silently weakening gates.
3. Classify an explicitly inserted target as an isolated release line **before any member can start or merge**, whether a later target is only planned/uncut or already has a line. Record this mode and exact verified released base with the goal/line using canonical identity, and make `target_of`, frontier, worker dispatch, `git.base`, PR target and `integrate` refuse member delivery while the line is absent or its source cannot be verified; do not fall back to integration. The owner explicitly approves creation, including canonical ID and exact historical base. Derive the base from recorded released provenance and Git ancestry, never from a syntactic fixed-depth prefix, and show the owner the immutable SHA, source release and current production tip. For example, `2.0.0.1` and then `2.0.1` each use the appropriate actually released baseline. If any member was already completed against integration before classification, detect that from checkpoint/merge/target provenance and block line activation rather than treating it as present: retain its history and require an explicit reviewed backport/new or reopened work item on the isolated line, or report a human resolution; never rewrite or cherry-pick it silently. Detect in-flight work and retarget races via goal/line records and leases; require a fresh exact target/base check on dispatch, before PR creation and integration, and reject stale attempts, preserving their work for review. Apply this isolation even when later release 3 is not cut but its work already reached integration.
4. Bind creation to the owner-approved **immutable source SHA** and source-release evidence, not to a moving production label. Before publishing the new line, validate on the remote that the SHA still resolves to the approved released baseline and compare current production and the original preview. Create the new ref only if absent with a conditional update; immediately re-read production and the new ref before marking the line verified or releasing the member-work gate. An intervening direct external production advance must never change the line's approved SHA. If the previewed production has advanced, keep member dispatch blocked and require a fresh preview/approval that classifies the line as current-production patch or isolated maintenance; no silent retarget or automatic deletion of the created ref. Every later delivery/integration and finish checks the current line ref and the recorded source; on mismatch pause for explicit recovery. A source advance after verification does not change that immutable baseline; if it affects production promotion, reclassify and reapprove before a production write. Where the remote cannot support the required atomic compare on a write, do not emulate it with an unguarded check-then-push: pause and report the limitation. Test direct remote source advances at preflight, between preflight/ref creation, before verification, during member work and immediately before promotion.
5. Give inserted lines their own recorded `inserted` mode in the configured release graph, with clear `current-production` versus isolated `maintenance` finish targets. Update the graph and `git.line_sync`: for this mode, pre-`approve_finish` sync records/validates the exact line tip but does **not** merge into integration, production or any later release. Approval presents the exact line head, source, finish target and any proposed forward-propagation destinations. A current-production patch may move production only after owner approval and a checked fast-forward merge whose expected target SHA is enforced atomically by the remote; if production advanced, the compare fails and approval must be refreshed. Verify the candidate is a descendant of the expected production SHA, so any lease guard cannot authorize a rewind. Do not bypass branch protection to gain atomicity; where the provider cannot guarantee the required target comparison, stop for a supported protected-branch/owner flow. Only after a successful authorized finish may the operation forward the approved patch to integration and relevant open later lines, each with explicit per-target eligibility, exact-head/CAS guards, visible partial state and reviewed conflicts. Never use a stale head or overwrite a later line. For an **older maintenance release after production has advanced**, finish the isolated retained release line without changing the main production branch or silently merging it backwards; any optional forward-port is a separately explicit reviewed action and never implies deployment. Already-cut/closed target aliases remain protected from duplicate lines. Serialize engine-controlled operations via existing leases and idempotent compare-and-set, but do not pretend those leases serialize external Git pushes. Preserve full canonical components in ref names, flow state and collision checks at arbitrary depth; no fixed-depth naming assumptions. For policies without branching, support identity/ordering but report the need for a suitable isolated line rather than claiming safe parallel patch delivery.
6. Implement as a named engine capability required by a reviewed policy update before any writer produces dotted strings, a dotted `flow.name` at any depth, new line state, or modified ledger/trailers. No old writer may truncate or misinterpret an internal zero component. Old engines must refuse writes on the upgraded policy, not ignore unknown targets or sort them numerically incorrectly. Preserve old goals, policy numeric fields, existing branch names and commit histories; no wholesale rewrite is needed. Before activation, inspect already-existing remote release refs and line records for alias collisions or noncanonical names. A collision is a surfaced blocker requiring explicit owner resolution, not an automatic rename or force push. Document upgrade order, staged policy adoption, rollback constraints once dotted state exists, and how custom workflows/branches adopt the new behavior; unrelated broken migration mechanisms are a separate goal.

## Concrete CLI, approval and compatibility contracts

Follow the existing `release cut N --answer F` and `hotfix start X --answer F` pattern while distinguishing early inserted-line creation from cutting a completed ordinary release:

- `zzzops release insert <TARGET> --from <SOURCE_RELEASE>` is a read-only preview when `--answer` is absent. Both identifiers use the same dotted parser and canonicalization. It requires the reviewed capability and branching policy described below. It does not change refs, create a goal, reserve a lease, or trigger delivery. Its JSON contains `insert_preview` with `target`, `source_release`, `source_goal` (the unique completed release-line goal), `source_commit` (the immutable full Git SHA proven by that line's successful finished `production_merge` result), `production_ref`, `production_commit` (the freshly read full SHA), `mode` (`production_patch` or `maintenance`), `branch`, `later_lines`, `already_completed_members`, and `fingerprint` (a stable hash over all of these approval-bearing fields). It also contains `answer_template` with `decision`, `quote`, `decided_by`, and `fingerprint`. The preview makes no irreversible choice on the owner's behalf; it reports ambiguity, missing history, ref/alias collisions, unsafe branch rules and already-completed members as explicit blockers rather than inventing a baseline. An unbranched policy reports the existing branching prerequisite.
- `zzzops release insert <TARGET> --from <SOURCE_RELEASE> --answer <F>` validates an answer with `decision: "approved"`, nonempty verbatim `quote` and `decided_by`, and the exact preview `fingerprint`. Its source is the immutable full `source_commit` captured in the preview, not a moving remote ref, and it verifies that the named source goal is closed successfully and its `production_merge` record and Git ancestry prove that commit was released. When the recorded finished source is missing or cannot prove ancestry, stop and request explicit source-history recovery; do not infer from a numeric prefix, newest branch or Git tag. `source_release` is an existing completed release, not a raw SHA; requiring it makes nested backports reviewable. To insert `2.0.0.1` after finished release `2`, use `--from 2` regardless of textual nesting. A source on which a target was not based cannot be silently reinterpreted later.
- Immediately before the atomic push, re-read the goal and source records, branch aliases and production ref and recompute the preview fingerprint. If any approval-bearing input changed, refuse with `preview_stale`, show the fresh preview and request a fresh answer. The atomic push creates the canonical inserted `release/<TARGET>` line and its goal in `pending_verification` state from exactly `source_commit`, only if both destination refs are absent; it cannot claim atomicity over external updates to production. Re-read production and the created line after push, and use a CAS-protected goal-state update to mark the line `verified` only if production still matches the approved `production_commit` and the line still points to `source_commit`. If production advances or a line is edited across this window, leave the line `pending_verification`, block all member worker starts, base, merge and finish operations, and surface a new preview/approval or conflict recovery. There is no period where its members are runnable while verification is pending. A separate owner answer to the refreshed preview verifies the unchanged original source SHA and updates the recorded production SHA/mode; it never silently creates a second branch or rewrites a ref. Repeated identical successful submissions recover the same canonical line; a mismatched answer or alias returns a refusal, not a second identity. If goal metadata changes concurrently, CAS fails and re-preview is required.
- `mode` is `production_patch` only when the approved source commit is the current production tip; if production is known to have advanced beyond that source and source ancestry is verified, the mode is `maintenance` and the main production ref is never moved. An unrelated or unprovable production ancestry is a blocker. This decision is bound into the answer fingerprint, revalidated on the remote before the finish, and never silently changed. Production finish and each authorized forward-port use the graph's exact-head approval and the guarded atomic destination checks described above. Old completed members found on integration keep their records; they are not treated as patch members on the new line and require separately reviewed backport/reopen work. No old goal is rewritten or automatically cherry-picked by insertion.
- The capability name is `insertable_release_targets`, defined by `engine/capabilities/insertable_release_targets.txt`. Install/upgrade every engine writer first; then a separately reviewed policy change adds `"insertable_release_targets"` to `settings.engine.requires`. Until that policy is in effect, the engine rejects `release insert` and non-integer new target writes and preserves the current integer-only behavior, including any legacy read-only diagnostics. Once it is required, pre-capability engines refuse writes using the existing `engine_too_old` guard before touching goal, lease, line or production refs. Capability activation itself does not migrate, rename or create branches, and aborts if existing line/ref aliases collide under canonicalization. Project policy/workflow updates remain reviewed and may be previewed with the existing policy tools. Refusal of unsafe/unknown mixed writers is a requirement, not a claim the old engine understands dotted labels.

These names and fields deliberately align with the existing CLI's `release` namespace, answer-file and branching settings; preserve existing `release cut <integer> --answer <F>` behavior. `next` surfaces a matching owner item when an inserted target needs a verified line and prints the preview command. `new --file`, `edit`, `next`, `show`, `validate`, `release cut` and line finish normalize aliases consistently; never encode numeric identifiers as JSON floats. Do not change unrelated releases, infer Git ancestry from dotted labels, deploy or publish.

## Test strategy

- Exercise parser and comparison properties for arbitrarily nested finite identifiers, including `2 < 2.0.0.1 < 2.0.1 < 2.1`, further insertions between adjacent already-known targets, aliases (`2.0.1.0` = `2.0.1`, `2.0` = `2`), preservation of internal zeros, deep canonical branch/ref round-trips and `2.1` vs `2.10`; also cover invalid floats/booleans/negative or malformed strings, ref safety, bounded components, canonical JSON/CLI/trailer round-trips, legacy integer policy/goals and collision detection. Test duplicate cuts/retries across alternate spellings produce one goal/ref.
- Real isolated Git remote fixtures: create a production release 2, cut release 3 and retain unreleased work on its line, then insert `2.1` from the verified production 2 base. Separately insert and deliver nested `2.0.0.1` before a cut `2.0.1` and `2.1`, verifying the source baseline by recorded Git ancestry and forwarding the patch without contaminating later lines. Merge patch goals to 2.1 and prove its tree excludes 3-only work, finish only after approval, and verify patch propagation to production, integration and 3 while preserving 3 content and assigned goals. Cover conflicts, racing creation, partial failures, stale refs, exact-head approval, already-advanced production, held/closed/dependency states and no-branch policies. Demonstrate ordinary integer release workflows remain unchanged.
- Exercise existing later-only commits already on integration with the later target uncut and cut; an inserted patch must remain based on its independently verified baseline. Race explicit insertion/retarget with worker dispatch and integration, including an already completed member on integration: no member is silently delivered to the wrong branch or falsely marked complete. Verify a retained work item is routed to explicit reviewed recovery.
- Real remote race fixtures move production after preview, between conditional line creation and verification, before a member dispatch, and immediately before finish. Verify no stale line is accepted without reapproval, no member proceeds against an unverified ref, no unguarded check-then-push changes production, and no direct external push can cause a rewind or wrong-base promotion. Include remote inability to atomically compare the destination and branch protection refusal.
- Assert inserted-mode `git.line_sync` records the exact patch head without changing integration, production, or later release refs before `approve_finish`; after approval, assert guarded propagation and safe partial failure. With production already at 3, create and finish an isolated 2.1 maintenance line from recorded release-2 ancestry, prove production remains on 3, and require separately approved forward-port.
- Drive the exact `release insert <TARGET> --from <SOURCE_RELEASE>` read-only preview and answer-file action in a real local Git remote: assert all approval-bearing fields and fingerprint, canonical alias idempotence and capability policy gating. Deterministically advance the remote production ref between preview, immediately-before-push, atomic line/goal creation and post-push verification. Check stale fingerprints/refusals, pending state and that no member agent/PR/merge starts before a fresh approval has verified the unchanged immutable baseline. Race source-goal metadata updates and two insert requests, and exercise source history missing/ambiguous, unsafe ancestry and completed members already on integration. The implementation must not pretend an atomic cross-ref check exists on a remote that cannot guarantee it.
- Exercise old/new writer combinations with the capability policy enabled and disabled; legacy readers must not silently mutate dotted state. Test activation refusal for alias collisions and no rewrite of existing histories. Run focused real-engine tests first, then existing integration/CLI tests and repository-required checks; do not contact or change real production branches.

## Scope and risks

Goal target labels and release-branch workflow only; semantic-version calculation, tags, package publishing, deployment, automatic production promotion, and unrelated migration repairs remain out of scope. Patch isolation must be proven from actual Git ancestry, not a label; alias canonicalization must precede storage, membership and ref operations; and empty/legacy portfolios must not lose their current behavior. Concurrent release lines and partial propagation are the highest-risk cases and require real Git/remote tests.
