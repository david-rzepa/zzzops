# G1051 test review

The checkpoint exercises useful real-engine identity behavior and uses throwaway bare Git remotes for initial insertion and older-maintenance checks. Its measured 44.829 s is a red, pre-implementation run and does not establish that feature journeys pass. I independently ran the nine identity/CLI tests at `ab1e7c1`; they ran in 0.556 s and failed on the integer-only baseline. The 44.829 s total is plausible for repeated real release workflows, and the race barrier is bounded and checks process exit; I did not find a measured disproportionate sleep to remove. The following gaps must be addressed before the tests are accepted.

1. **Opt-in contradiction.** `.agents/test_engine_insertable_releases.py:84-99` runs two real CLI dotted-goal tests in `Branching`'s default policy without enabling `insertable_release_targets`. The approved design requires rejecting all new dotted writes before that capability is required, and `.agents/test_engine_insertable_release_journeys.py:275-283` explicitly asserts that rejection. A correct implementation therefore cannot satisfy both tests. Enable the feature policy before positive CLI cases, retain the separate negative test, and keep true legacy cases exercised unactivated.
2. **Missing successful production patch/propagation.** The first journey creates an isolated line and checks its base, but never delivers a patch, finishes it, or verifies approved propagation; the only finish journey is maintenance, which deliberately must not change production. Thus an implementation can create lines correctly but fail every normal patch finish or corrupt later-release/integration state while the suite passes. Add a real bare-remote production-patch journey that delivers an actual patch, checks pre-approval no-forwarding, verifies exact approved production finish and later-line/integration propagation without contaminating their existing content/goal assignments, including nested insertion. Exercise a conflict/partial propagation or other explicitly specified refusal.
3. **Safety-critical real-remote interleavings uncovered.** The only injected barrier is before initial atomic creation and changes production (`test_external_production_advance_during_atomic_line_creation_stays_pending`); the finish test advances production before invoking finish, not between its last read and destination update. The accepted design distinguishes production-only, source-goal-only and patch-destination-only changes after final reads; allows only provisional isolated line updates for the first two; requires destination CAS failure for the third and for post-approval production advancement; and requires atomic source-verify/destination-update or safe refusal for unsupported providers. Without tests at those actual write boundaries, a check-then-push implementation can pass while losing concurrent changes or releasing revoked provenance. Add deterministic real-remote tests at those boundaries, including the local-server atomic transaction and unsupported-provider refusal, and assert unchanged production/forward-port refs where required. Avoid adding unbounded sleeps.
4. **Missing target integrity and compatibility cases.** Current tests do not exercise an existing alias/ref collision at capability activation, a completed member already delivered to integration before an inserted line is classified, stale dispatch/retarget races, dependency ordering with later targets, or the no-branch policy. These are explicitly required by the approved design; violations could create duplicate lines, falsely mark an absent patch complete, silently route work to integration, or deadlock earlier work. Add focused real-engine or minimal real-remote tests demonstrating correct refusal/blocking and preservation of existing records. Include a legacy integer workflow after feature activation and real `edit`/`cut` alias handling; the current real integer source is constructed before activation.

The existing CLI/remote scaffolding and the red capability guard are useful; keep them, and measure the expanded meaningful tests without presenting a red baseline as implementation evidence.
