# G1051 test re-review

The positive CLI tests now enable the capability, retain negative pre-opt-in coverage, and include a legacy integer release after opt-in. The added bare-remote production patch completes and propagates to main, integration and a later line without the later line's changes appearing in production; a conflicting forward-port case also checks preserved refs and visible blockage. The test suite adds alias collision, no-branch, retargeted work and dependency cases, plus deterministic patch-destination/production/source interleavings and a protected remote rejection. These resolve substantial portions of the original findings.

The exact-checkpoint 30-case run is honestly reported red at 72.842 s; feature-specific races stop at the absent capability, so this is not evidence that those paths pass. An independent local run of the invalid-identifier case passed on `6248216` in 0.015 s. The expanded cost is attributable to individual real Git/CLI release journeys; bounded barriers poll without fixed long sleeps. The following material coverage gaps remain:

1. **Refreshed source authority and an actual cross-ref transaction.** `_interleave_patch_merge` changes the source-goal document but does not check that the new source/approval state is detected by a refreshed review, does not attempt promotion or forward-port after the move, and never exercises a real source-verify/destination-update transaction or a provider lacking it. Its assertion that `finish` is not immediately in `next` can pass merely because line sync and finish approval have not occurred; it does not prove revocation or fresh-authority gating. Likewise, the production/source-only branches merely assert the patch ref exists (it existed before the race), so they do not establish what became of the attempted update. An implementation that ignores source revocation and then promotes stale work can satisfy these checks. Test the subsequent actual source check/approval and promotion refusal, assert the full allowed outcome of provisional line advancement, and use a real server transaction to verify source revocation atomically blocks destination update; test fail-closed behavior for unsupported providers when this guarantee is required. The test author is correct that the approved design does not name a concrete policy selector or adapter for this stricter mode. If no existing public contract can express it, send a precise design finding to specify the smallest testable contract; do not invent production APIs or test Git alone instead of the engine.
2. **Completed integration member is only previewed.** `test_completed_integration_member_requires_explicit_recovery_before_insertion` verifies a read-only preview reports the old completed member and that the preview itself creates no branch. It never supplies approval or attempts the mutating insertion. An implementation that warns during preview but accepts the answer and activates the line with that already-completed integration-only goal can pass, falsely implying the patch is included. Exercise the actual insertion/activation attempt with an approved preview where permitted and assert refusal or a real blocked recovery state, the old member and work history remain intact, and the member cannot be counted/delivered as part of that line until explicit reviewed recovery.

Do not interpret these findings as requiring a particular additional sleep or fabricated adapter. Test the observable end-to-end contract and preserve the already accepted real-Git fixtures.
